| Шаг | Windows | Linux |
| --- | --- | --- |
| 1. Зависимости | `python -m venv .venv`; `.\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt`; `cd frontend; npm install` | `python3 -m venv .venv`; `./.venv/bin/pip install -r backend/requirements.txt`; `cd frontend && npm install` |
| 2. Конфигурация | `Copy-Item .env.example .env`, удалить строки `APP_DATA_DIR` и `DATABASE_URL`, сменить пароль первого админа | `cp .env.example .env`, то же |
| 3. Запуск | `.\start.ps1` (или вручную: `cd backend` + uvicorn, затем `cd frontend` + `npm run dev`) | вручную: `cd backend && ../.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000`, затем `cd frontend && npm run dev` |

`start.sh` в текущем виде рассчитан на Git Bash в Windows: он ищет `.venv/Scripts/python.exe`. На Linux используйте ручной запуск.

## 1. Режимы развёртывания

Режимов два: прямой запуск (два процесса: uvicorn + Vite) и Docker (один контейнер с backend). Автозапуска после перезагрузки, службы Windows, systemd-юнита и обратного прокси в репозитории нет. Frontend в обоих режимах поднимается отдельно: backend не раздаёт статику и не содержит собранного UI.

### 1.1. Что общего

| Элемент | Факт |
| --- | --- |
| Конфигурация | Ровно один `.env` в корне репозитория. `backend/app/config.py` читает `PROJECT_ROOT/.env` независимо от рабочего каталога процесса |
| Данные | `<APP_DATA_DIR>/hackathon.db` (+ `-wal`, `-shm` при работе), `<APP_DATA_DIR>/documents/<project_id>/`, `<APP_DATA_DIR>/backups/`. Если `APP_DATA_DIR` и `DATABASE_URL` не заданы, каталог — `<корень репозитория>/data` (абсолютный путь, не зависит от CWD) |
| Схема БД | Миграции Alembic применяются автоматически при старте процесса (8 ревизий), вручную запускать не обязательно |
| Bootstrap | При пустой таблице `users` создаются первый админ (`APP_FIRST_ADMIN_*`), проект `Hackathon` (id=1) и 9 стартовых колонок |
| API | Префикс `/api/v1`; `GET /health` без префикса и без аутентификации; `/docs` и `/openapi.json` тоже открыты |
| Фоновые задачи | Один daemon-поток внутри процесса uvicorn: тик 60 с, бэкап каждые 900 с |
| Порт backend | 8000 в скриптах и Docker; `APP_HOST`/`APP_PORT` из `.env` нигде не используются |
| Порт UI | 5173 у `npm run dev`; Vite проксирует `/api` и `/health` на `http://127.0.0.1:8000` |
| Логи | Только stdout/stderr процесса. Файлов логов, ротации и журнала операций нет |
| Секреты | `.env` (не коммитится, в бэкапы не попадает) |

### 1.2. Прямой запуск, Windows

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
Copy-Item .env.example .env
# отредактировать .env (см. 2.1), затем:
.\start.ps1
```

`start.ps1` при первом запуске создаёт venv и ставит зависимости, при отсутствии `frontend/node_modules` делает `npm install`, затем открывает два окна: uvicorn в `backend/` на `127.0.0.1:8000` и `npm run dev` в `frontend/`. `start.bat` делает то же через `cmd`. Скрипты не создают `.env`, не проверяют его содержимое и всегда печатают учётные данные по умолчанию (`admin / change-me`), даже если в `.env` заданы другие.

Ручной запуск (когда нужен контроль над логами):

```powershell
cd backend
..\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
# второе окно
cd frontend
npm run dev
```

Backend обязан запускаться из `backend/` (пакет `app` лежит там) либо с `--app-dir backend` из корня. Это важно для относительных путей в `.env`: `./data` в `DATABASE_URL`/`APP_DATA_DIR` разрешается от текущего каталога процесса, поэтому при запуске из `backend/` данные уедут в `backend/data/`. Подробнее — в 2.1.

Что появится при первом старте:

| Объект | Признак |
| --- | --- |
| `data/hackathon.db` | файл ~270 КБ; рядом `-wal` и `-shm`, пока сервер работает |
| `data/backups/` | появится не сразу, а после первого бэкапа (примерно через 15 минут) |
| `data/documents/` | создаётся при первом сохранении документа |
| Админ | логин/пароль из `.env`; в журнале аудита запись `bootstrap.admin_created` |
| Проект | `Hackathon`, состояние `preparation`, 9 колонок от `backlog` до `trashed` |

### 1.3. Прямой запуск, Linux

```bash
python3 -m venv .venv
./.venv/bin/pip install -r backend/requirements.txt
cp .env.example .env
cd backend && ../.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
# второе окно
cd frontend && npm install && npm run dev
```

`start.sh` на Linux не работает (путь `.venv/Scripts/python.exe` — от Windows-venv). Для внешнего доступа по сети меняйте `--host` осознанно: без туннеля и TLS приложение не предназначено для публикации.

### 1.4. Docker

```powershell
Copy-Item .env.example .env   # отредактировать секреты
docker compose up --build -d
docker compose ps
docker compose logs -f app
```

| Параметр | Значение |
| --- | --- |
| Образ | `python:3.12-slim`, в него копируется только `backend/`; frontend в образ не входит |
| CMD | `uvicorn app.main:app --host 0.0.0.0 --port 8000` |
| Порт | `8000:8000` на localhost |
| Переменные | `env_file: .env`, поверх него `APP_DATA_DIR=/data`, `DATABASE_URL=sqlite:////data/hackathon.db` |
| Данные | bind-mount `./data:/data`; база, документы и бэкапы остаются на хосте |
| Политика | `restart: unless-stopped` — перезапуск при падении процесса, но не при статусе `unhealthy` |
| Healthcheck | `python -c "urllib.request.urlopen('http://localhost:8000/health')"`, interval 15 с, timeout 5 с, retries 3, start_period 30 с |
| Пользователь | процесс в контейнере работает от root: на Linux-хосте созданные файлы будут принадлежать root |

Ограничения Docker-режима:

- UI в контейнере нет: после `docker compose up` доступен только API. UI запускается на хосте (`cd frontend; npm install; npm run dev`) и проксирует запросы на `127.0.0.1:8000`.
- `.dockerignore` отсутствует, поэтому в контекст сборки попадают `data/`, `.venv/`, `.git/`. Содержимое образа это не меняет (копируется только `backend/`), но сборка замедляется.
- На Linux после запуска контейнера прямой запуск от обычного пользователя может не иметь прав на `data/` (владелец root). Лечится `sudo chown -R $USER:$USER data` при остановленном контейнере.
- `docker compose down` не удаляет `./data`; `down -v` для bind-mount тоже безопасен, но удалять каталог `data/` вручную нельзя.

### 1.5. Порты и адреса

| Адрес | Что | Доступность |
| --- | --- | --- |
| `http://127.0.0.1:8000/api/v1` | API | localhost (Docker — все интерфейсы через mapping) |
| `http://127.0.0.1:8000/health` | проверка живости | без сессии |
| `http://127.0.0.1:8000/docs` | Swagger UI | без сессии |
| `http://localhost:5173` | UI (Vite dev) | localhost; проксирует `/api` на 8000 |
| `http://localhost:4173` | UI после `npm run build && npm run preview` | не проверялось в этом проекте |
| `https://<subdomain>.fxtun.ru` | публичный адрес | не реализовано, см. раздел 6 |

### 1.6. Логи

| Режим | Где смотреть |
| --- | --- |
| Прямой запуск | окно uvicorn (access log и traceback); окно Vite — ошибки сборки и прокси |
| `start.ps1` / `start.bat` | отдельные окна `HCC Backend` / `HCC Frontend`; закрытие окна убивает процесс |
| Docker | `docker compose logs -f app`, `docker compose logs --since 1h app` |

Приложение почти не пишет собственных сообщений: старт, применение миграций и bootstrap проходят молча; ошибки фонового потока глушатся (`except Exception: pass`), поэтому их в логах не видно. Telegram-мок логирует на уровне INFO, а корневой логгер uvicorn не настроен (порог WARNING), поэтому строки `[telegram mock]` обычно не появляются вообще.

### 1.7. Остановка

| Режим | Команда | Замечания |
| --- | --- | --- |
| Прямой, окно uvicorn | `Ctrl+C` | штатное завершение: срабатывает `stop`-событие планировщика |
| `start.ps1` / `start.bat` | закрыть оба окна | это жёсткое завершение процесса; на диске могут остаться каталоги `.tmp_*` в `data/backups/` |
| `start.sh` | `Ctrl+C` в терминале | дочерние процессы получают сигнал вместе с группой |
| Docker | `docker compose stop` (или `down`) | данные в `./data` сохраняются |

Перед остановкой на время (перенос, обслуживание) сделайте ручной бэкап: автоматический мог ещё не сработать. Прерывание в момент создания копии не портит `latest.zip` (он подменяется через временный файл), но может оставить неполный `backup_*.zip`, на который нет записи в БД; следующая копия удалит такие файлы.

## 2. Первичная настройка

### 2.1. Файл `.env`

`.env` создаётся копированием `.env.example`. Значения по умолчанию безопасны только для локального запуска на своей машине.

| Переменная | Значение по умолчанию | Фактическое использование |
| --- | --- | --- |
| `APP_ENV` | `development` | читается в настройки, ни на что не влияет |
| `APP_SECRET_KEY` | `change-me` | **не используется**: cookie — случайный токен, в БД хранится его sha256 |
| `APP_HOST`, `APP_PORT` | `127.0.0.1`, `8000` | **не используются**: адрес и порт заданы в скриптах, Dockerfile и compose |
| `APP_DATA_DIR` | `./data` | каталог данных; относительный путь считается от CWD процесса |
| `DATABASE_URL` | `sqlite:///./data/hackathon.db` | если задан — используется как есть; если пуст/отсутствует — `sqlite:///<APP_DATA_DIR>/hackathon.db` |
| `APP_FIRST_ADMIN_LOGIN` / `_PASSWORD` / `_NAME` | `admin` / `change-me` / `Administrator` | только при создании первого админа, когда таблица `users` пуста |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | пусто | читаются Telegram-клиентом; реальной отправки нет, при заданных значениях поведение то же (лог-заглушка) |
| `AI_GEMINI_API_KEY`, `AI_DEEPSEEK_API_KEY`, `AI_PRIORITY_PROVIDER` | пусто, `gemini` | **не используются**: ИИ работает на mock, провайдер хранится в настройках проекта |
| `GOOGLE_DRIVE_FOLDER_ID` | пусто | **не используется** |
| `FXTUNNEL_TOKEN` | пусто | **не используется** |

Обязательные правки перед первым запуском:

1. `APP_FIRST_ADMIN_PASSWORD` — сменить с `change-me` на длинный пароль.
2. `APP_DATA_DIR` и `DATABASE_URL` — удалить или закомментировать обе строки, если данные должны лежать в `<корень репозитория>/data`. Значение `./data` из примера разрешается от текущего каталога: при запуске из `backend/` база уйдёт в `backend/data/`, и прямой запуск перестанет видеть данные Docker и прежние данные в корне. Пустое `APP_DATA_DIR=` тоже неверно: `Path("")` — это текущий каталог.
3. Если данные нужны на другом диске — задать только абсолютный `APP_DATA_DIR` с прямыми слэшами (`D:/hcc-data`) и не задавать `DATABASE_URL`.

Проверка фактических путей без запуска сервера (из `backend/`):

```powershell
cd backend
..\.venv\Scripts\python.exe -c "from app.config import settings; print(settings.data_dir.resolve()); print(settings.sqlalchemy_url)"
```

Путь в выводе должен совпадать с каталогом, где лежат `hackathon.db` и `backups/`.

### 2.2. Первый админ

Первый администратор создаётся один раз — при старте, если в таблице `users` нет ни одной записи. Ему выдаётся глобальная роль `admin` (`project_id = NULL`), создаётся проект `Hackathon` и 9 стартовых колонок, в аудит пишется `bootstrap.admin_created`.

Следствия, важные при сопровождении:

- Изменение `APP_FIRST_ADMIN_*` после первого старта ничего не делает: пароль хранится bcrypt-хешем, значения из `.env` больше не читаются.
- Если в БД уже есть хотя бы один пользователь (например, восстановили базу без админа), bootstrap не сработает.
- Пароль принимается любой длины от 1 символа: политики сложности нет, ответственность на администраторе.

### 2.3. Смена пароля

Штатный путь — только через администратора: `Админ → Пользователи → «пароль»` (или `POST /api/v1/admin/users/{id}/password-reset` с `{"new_password": "..."}`). Старый пароль не запрашивается; все активные сессии пользователя отзываются. Самостоятельной смены пароля в UI и API нет.

Потерян пароль единственного админа — восстановление при остановленном сервере, из `backend/` (пути к БД берутся из того же `.env`, поэтому запускать нужно в том же каталоге, что и сервер):

```powershell
cd backend
@'
from app.db.session import SessionLocal
from app.db.models import Session as SessionModel, User
from app.security import hash_password
db = SessionLocal()
u = db.query(User).filter(User.login == "admin").one()
u.password_hash = hash_password("NEW-STRONG-PASSWORD")
db.query(SessionModel).delete()
db.commit()
print("password reset for", u.login)
'@ | ..\.venv\Scripts\python.exe -
```

Если админ есть, но потеряна роль `admin` (или единственный админ деактивирован), добавьте назначение роли:

```powershell
@'
from app.db.session import SessionLocal
from app.db.models import Role, RoleAssignment, User
db = SessionLocal()
u = db.query(User).filter(User.login == "admin").one()
u.active = True
if not db.query(RoleAssignment).filter_by(user_id=u.id, role=Role.admin, revoked_at=None).first():
    db.add(RoleAssignment(user_id=u.id, role=Role.admin, project_id=None, granted_by=None))
db.commit()
print("admin role granted")
'@ | ..\.venv\Scripts\python.exe -
```

Крайняя мера — удалить `data/hackathon.db` при остановленном сервере и запустить его снова: база и админ создадутся заново, но все задачи, время, документы (записи в БД) и журналы будут потеряны. Применяйте только если данные не нужны.

### 2.4. Пользователи и роли

| Действие | UI | API | Кто может |
| --- | --- | --- | --- |
| Создать пользователя | `Админ → Пользователи → + Пользователь` | `POST /api/v1/admin/users` | admin |
| Сменить логин/имя/Telegram | в UI только просмотр | `PATCH /api/v1/admin/users/{id}` | admin |
| Сбросить пароль | кнопка «пароль» | `POST .../password-reset` | admin |
| Деактивировать | кнопка «отключить» | `POST .../deactivate` | admin |
| Назначить роль | кнопки «участник/капитан/админ» | `POST /api/v1/admin/roles` | admin |
| Отозвать роль | крестик рядом с бейджем роли | `DELETE /api/v1/admin/roles/{id}` | admin |
| Журнал входов | `Админ → Журнал входов` | `GET /api/v1/admin/login-events` | admin |
| Блокировка IP | `Админ → IP-ограничения` | `POST /api/v1/admin/ip-rules` | admin |
| Снять блокировку IP | в UI нет | `DELETE /api/v1/admin/ip-rules/{id}` | admin |
| Сбросить лимит попыток | кнопка «Сбросить лимит» | `POST /api/v1/admin/ip-rules/reset?ip=...` | admin |

Правила, зашитые в код:

- Роли складываются: пользователь может быть одновременно `participant` и `captain`. Любая из ролей даёт доступ к рабочим данным; `captain`/`admin` дополнительно дают корректировку времени, бэкапы, запуск фоновых задач и голосование за завершение.
- `admin` — глобальная роль (`project_id = NULL`), `participant`/`captain` по модели привязаны к проекту. Однако UI назначает их без `project_id`, а проверки прав проект не учитывают: фактически роли действуют на все проекты.
- Нельзя деактивировать последнего активного админа и отозвать его роль — ошибка `409 LAST_ADMIN`.
- Деактивация отзывает все роли и сессии. Обратной операции «активировать» нет: в UI и API её нет, только правка БД (см. 2.3).
- Пароли хранятся bcrypt, в API не возвращаются. Ограничение входа: 5 неудач на логин и 10 на IP за 15 минут, затем `429 RATE_LIMITED`; сессия — 7 дней.

### 2.5. Проект по умолчанию и дедлайн

- Проект `Hackathon` (id=1) создаётся bootstrap-ом в состоянии `preparation`. UI запоминает выбранный проект в `localStorage` под ключом `hcc-project` (по умолчанию 1). Если после восстановления проекта с таким id нет, списки и доски будут пустыми или вернут 404 — переключите проект в выпадающем списке.
- Новый проект создаёт только админ: `Настройки → Создать новый проект`. Проект всегда создаётся в `preparation` с 9 колонками; отдельного API «перевести в active» нет.
- Дедлайн задаёт только админ: `Настройки → Дедлайн` (браузер отправляет время в UTC, в БД хранится наивный UTC, отображается в локальном времени). Дедлайн используется в KPI, рисках и снимке для ИИ; никаких фоновых действий по дедлайну нет — уведомление о приближении дедлайна не реализовано.
- Название проекта меняет капитан или админ (`PATCH /api/v1/projects/{id}`).

### 2.6. Колонки и модули

| Объект | Где | Ограничения |
| --- | --- | --- |
| Колонки | `Настройки → Колонки доски` | 9 стартовых колонок удалить нельзя (`409 COLUMN_PROTECTED`), переименовывать и менять флаги можно; удаление пользовательской колонки переносит её задачи в `backlog` |
| Флаги колонки | чекбоксы «авто-старт»/«авто-стоп» | применяются только при перемещении задачи в эту колонку: авто-старт запускает таймер, если он не идёт; авто-стоп останавливает идущий таймер |
| Модули | `Настройки → Модули` | создание, переименование, удаление; при удалении задачи остаются без модуля; светофор модуля считается по инцидентам |
| Песочница | `Песочница` (admin) | создаёт проект `Sandbox` в состоянии `active`, реальных пользователей `alice`, `bob`, `cap` с паролем `sandbox-pass` и назначенными ролями |

### 2.7. Состояние проекта и режим только для чтения

Состояния: `preparation` (создание), `active` (только у проекта песочницы), `completed` (завершён). Переход в `completed` и обратно — только единогласным голосованием: `Настройки → Завершение хакатона` или `POST /api/v1/projects/{id}/completion-votes` с `{"action": "complete"}` / `"reopen"`. Требуется голос каждого активного капитана и админа (список глобальный, без учёта проекта); голоса не отзываются, после смены состояния обнуляются.

В состоянии `completed` возвращают `409 PROJECT_COMPLETED`: создание и изменение задач, перемещение, таймеры, корректировка времени, создание и обработка инцидентов. Документы, колонки, модули, название и дедлайн проекта при этом по-прежнему изменяемы.

## 3. Бэкапы

### 3.1. Виды копий и расписание

| Вид | Когда создаётся | Обновляет `latest.zip` | Хранение |
| --- | --- | --- | --- |
| `automatic` | Планировщик: каждые 900 с после старта процесса; первый — примерно через 15 минут | да | Хранится одна обычная копия: предыдущая удаляется |
| `manual` | Кнопка `Админ → Резервные копии → Создать бэкап` или `POST /api/v1/admin/backups` | да | Так же: вытесняет предыдущую обычную |
| `safety` | Автоматически перед каждым восстановлением | нет | Не удаляется никогда |

Важные следствия расписания:

- Отсчёт 900 с начинается заново при каждом старте: если сервер перезапускается чаще, чем раз в 15 минут, автоматические копии не создаются вообще. После каждого перезапуска делайте ручной бэкап.
- При ошибке создания (нет места, БД занята) запись не появляется, а попытка повторяется каждый тик (60 с), пока не удастся.
- Записи о копиях лежат в таблице `backup_records` той же БД: восстановление откатывает и историю копий.
- Google Drive и любая внешняя копия не реализованы: единственная защита — локальный каталог на том же диске.

### 3.2. Где лежат и что внутри

```
data/backups/
  backup_20261027131357625135_automatic.zip   # имя: backup_<UTC YYYYMMDDHHMMSSffffff>_<kind>.zip
  latest.zip                                  # побайтовая копия последней automatic/manual
```

Внутри архива: `database.sqlite` (согласованный снимок через SQLite backup API, включая данные из WAL), `documents/` (если каталог существовал) и `manifest.json` вида `{"created_at": "<UTC ISO>", "kind": "automatic"}`. Версия схемы в манифест не пишется.

Каждая копия регистрируется в `backup_records`: `path`, `checksum` (sha256 всего zip), `size_bytes`, `kind`, `created_at`. Запись создаётся **после** записи архива, поэтому внутри архива её нет: после восстановления в списке не будет записи о самой восстановленной копии и о `safety`-копии, хотя файлы остаются на диске.

### 3.3. Ручной бэкап

UI: `Админ → Резервные копии → Создать бэкап`. API (капитан или админ):

```powershell
$s = New-Object Microsoft.PowerShell.Commands.WebRequestSession
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/v1/auth/login -ContentType application/json -Body '{"login":"admin","password":"<пароль>"}' -WebSession $s
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/v1/admin/backups -WebSession $s
```

Требования: свободное место не меньше двух объёмов `data/` (создание копии + `latest.zip`), отсутствие активной тяжёлой записи. Копия делается без остановки сервера.

### 3.4. Проверка целостности

Список и контрольные суммы (в UI колонки `checksum` нет, только ID/время/тип):

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/v1/admin/backups -WebSession $s |
  Format-Table id, kind, size_bytes, checksum, created_at
```

Сверка файла и распаковка без влияния на рабочие данные:

```powershell
(Get-FileHash data\backups\latest.zip -Algorithm SHA256).Hash.ToLower()   # сравнить с checksum из API
$t = Join-Path $env:TEMP 'hcc-verify'
Remove-Item $t -Recurse -Force -ErrorAction SilentlyContinue
Expand-Archive data\backups\latest.zip -DestinationPath $t
Get-Content "$t\manifest.json"
..\.venv\Scripts\python.exe -c "import sqlite3,sys; db=sqlite3.connect(sys.argv[1]); print('integrity:', db.execute('pragma integrity_check').fetchone()[0]); print('users:', db.execute('select count(*) from users').fetchone()[0]); print('tasks:', db.execute('select count(*) from tasks').fetchone()[0]); print('backups:', db.execute('select count(*) from backup_records').fetchone()[0])" "$t\database.sqlite"
Remove-Item $t -Recurse -Force
```

Ожидаемый результат: `integrity: ok`, ненулевое число пользователей, число задач, соответствующее моменту копии. `sqlite3` CLI в системе не обязателен — используется Python из venv. Раз в неделю проверяйте не только `integrity_check`, но и реальное восстановление на копии данных (см. 3.5) — только оно подтверждает пригодность архива.

### 3.5. Восстановление через UI/API

UI: `Админ → Резервные копии → Восстановить` (кнопка доступна только в админском разделе). API (капитан или админ):

```powershell
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:8000/api/v1/admin/backups/<id>/restore `
  -ContentType application/json -Body '{"confirm":true}' -WebSession $s
```

Без `confirm: true` вернётся `422 CONFIRM_REQUIRED`. Порядок операций на сервере: проверка sha256 файла (`409 BACKUP_CORRUPT` при расхождении) → создание `safety`-копии текущего состояния → закрытие сессии и `engine.dispose()` → удаление `hackathon.db`, `-wal`, `-shm` → копирование `database.sqlite` из архива → полная замена `data/documents/` → `alembic stamp head` (без применения миграций) → `200`.

Предупреждения, которые нужно проговорить до нажатия:

| Риск | Что происходит |
| --- | --- |
| Замена на месте | Всё, что сделано после выбранной копии, теряется безвозвратно: задачи, время, инциденты, пользователи, сессии, аудит, история бэкапов. Окна отката нет |
| Документы | Каталог `documents/` заменяется целиком: файлы, созданные после копии, исчезают, а записи о них — вместе с БД |
| Список копий | После восстановления список берётся из восстановленной БД: восстановленной копии и `safety`-копии в нём нет, файлы лежат в `data/backups/` |
| Схема | Миграции не применяются, схема только помечается актуальной. Восстанавливать копию от другой версии приложения нельзя — получите ошибки «no such column» |
| Сессии | Cookie, выданные после снимка, перестанут работать (`401 UNAUTHENTICATED`); часть пользователей останется в системе, если их сессии были в снимке |
| Перезапуск | Технически сервер продолжает работать (движок пересоздаёт соединения), но перезапуск рекомендуются: сбрасывается in-memory лимитер ИИ и снимаются подозрения о старых соединениях. При ручной замене файлов перезапуск обязателен |
| Одновременная работа | В момент замены БД другие запросы могут получить `500`. Восстанавливайте вне активной работы команды и не в момент автоматического бэкапа |

### 3.6. Ручное восстановление (сервер остановлен)

Применяется, когда API недоступен, БД повреждена или нужно откатиться на другой ПК.

```powershell
# 1. остановить backend
$t = Join-Path $env:TEMP 'hcc-restore'
Remove-Item $t -Recurse -Force -ErrorAction SilentlyContinue
Expand-Archive data\backups\backup_<...>.zip -DestinationPath $t

# 2. сохранить текущее состояние (на случай ошибки)
Copy-Item data data.broken -Recurse

# 3. заменить БД и документы
Remove-Item data\hackathon.db, data\hackathon.db-wal, data\hackathon.db-shm -Force -ErrorAction SilentlyContinue
Copy-Item "$t\database.sqlite" data\hackathon.db
Remove-Item data\documents -Recurse -Force -ErrorAction SilentlyContinue
if (Test-Path "$t\documents") { Copy-Item "$t\documents" data\documents -Recurse }

# 4. запустить сервер: миграции применятся автоматически
```

В Linux те же шаги с `unzip` и `rm -f data/hackathon.db*`. Если архив от другой версии приложения, перед запуском примените миграции вручную: `cd backend && ..\.venv\Scripts\python.exe -m alembic upgrade head` (для Linux — `../.venv/bin/python`).

### 3.7. Ограничения бэкапов

- Нет выгрузки во внешнее хранилище и нет шифрования: архив содержит хеши паролей, все документы и журналы. Обращайтесь с `data/backups/` как с секретом.
- `.env` не входит в бэкап — после переноса/восстановления на другом ПК конфигурацию нужно иметь отдельно.
- Обычных копий хранится одна; `safety`-копии не удаляются и постепенно занимают диск. Периодически чистите старые `*_safety.zip` вручную при остановленном сервере (учётные записи о них останутся в БД, но список в UI переживёт отсутствие файла — восстановление вернёт 404).
- Восстановление не проверяет, что копия старше текущих данных, и не делает diff: это всегда полный откат.

## 4. Перенос на другой ПК

| Копировать | Не копировать | Почему |
| --- | --- | --- |
| Код репозитория (без служебных каталогов) | `.venv/` | внутри venv абсолютные пути к интерпретатору |
| `.env` (отдельно от кода, как секрет) | `frontend/node_modules/` | пересобирается `npm install` |
| `data/` целиком: `hackathon.db`, `hackathon.db-wal`, `hackathon.db-shm`, `documents/`, `backups/` | `__pycache__/`, `.pytest_cache/`, `backend/tests/.tmp/` | мусор и кеши |
| `frontend/package-lock.json` (уже в репозитории) | чужой `backend/data/` | признак того, что данные когда-то писались не туда; разберитесь, какой каталог настоящий |

Порядок:

1. Остановить сервер на старом ПК (чтобы WAL был свёрнут и файлы не менялись).
2. Сделать ручной бэкап и убедиться, что он появился в списке.
3. Скопировать репозиторий, `.env` и `data/` (включая `-wal`/`-shm`, если они остались).
4. На новом ПК поставить Python 3.12 и Node.js, создать venv, выполнить `pip install -r backend\requirements.txt` и `npm install` в `frontend/`.
5. В `.env` удалить `APP_DATA_DIR`/`DATABASE_URL` (данные будут читаться из `<корень>/data`) или прописать абсолютный путь нового ПК. Старые абсолютные пути — самая частая причина «данные пропали».
6. Запустить backend и UI.
7. Проверить: `/health` = 200; вход под своим логином; список проектов и число задач; документы открываются; `Админ → Резервные копии` показывает прежние копии; `Get-FileHash` копии совпадает с `checksum` в API; состояния таймеров (см. 10.1).

Проверка числа сущностей без запуска сервера:

```powershell
..\.venv\Scripts\python.exe -c "import sqlite3; db=sqlite3.connect(r'data\hackathon.db'); print([(t, db.execute(f'select count(*) from {t}').fetchone()[0]) for t in ('users','projects','tasks','documents','backup_records')])"
```

## 5. Мониторинг и здоровье

### 5.1. Что фактически означает `/health`

| Аспект | Факт |
| --- | --- |
| Авторизация | не требуется; доступен и по `/health`, и через прокси Vite |
| Что делает | `SELECT 1` через соединение из пула и возвращает `200 {"status":"ok"}` |
| Что не проверяет | запись в каталог данных, наличие/целостность БД, применённые миграции, свободное место, фоновый поток, доступность документов и бэкапов |
| При недоступной БД | исключение не перехватывается: `500` с телом `Internal Server Error` (без конверта `{"error":...}`) |
| Смысл | liveness процесса и доступность БД, не readiness приложения |

`README.md` и `docs/03-architecture-and-operations.md` обещают проверку записи в каталог данных — этого в коде нет. Практический вывод: зелёный `/health` не гарантирует, что документы сохраняются и бэкапы создаются. Раз в сутки проверяйте запись файла и последний бэкап вручную.

### 5.2. Healthcheck в Docker

Compose-проверка вызывает `/health` через `urllib` каждые 15 с. Любой не-2xx ответ (включая 500) или сетевая ошибка считается неудачей; после 3 неудач контейнер получает статус `unhealthy`. `restart: unless-stopped` на статус `unhealthy` не реагирует — контейнер останется запущенным, но помеченным. Смотреть: `docker inspect --format '{{json .State.Health}}' <container>`.

### 5.3. Autoheal и Uptime Kuma

Не реализованы: в `docker-compose.yml` только сервис `app`, нет контейнера Autoheal, метки для него, Uptime Kuma, уведомлений в Telegram и внешних алертов. Требования `docs/03` в этой части не выполнены; `TELEGRAM_*` не влияет ни на что.

Если добавлять самостоятельно: Autoheal — отдельный контейнер с доступом к Docker socket и фильтром по метке приложения (доступ привилегированный, не давать другим контейнерам); Uptime Kuma — отдельный контейнер с постоянным томом, HTTP-проверка `/health` раз в 60 с и Docker-проверка контейнера, панель не публиковать через туннель. Автоматическое восстановление данных запрещено в любом случае: только перезапуск процесса и оповещение.

### 5.4. Пятиминутная проверка (во время хакатона)

| Проверка | Как | Норма |
| --- | --- | --- |
| Живость | `Invoke-RestMethod http://127.0.0.1:8000/health` или UI | 200, `{"status":"ok"}` |
| Вход | открыть UI в приватном окне, войти тестовым участником | вход проходит, роли видны |
| Доска | открыть проект, переместить тестовую задачу | нет 409/500, таймер реагирует на флаги колонки |
| Свежесть бэкапа | `Админ → Резервные копии`, верхняя строка | моложе 20 минут; иначе создать вручную |
| Место на диске | `Get-PSDrive D`.Free | больше 1 ГБ; `safety`-копии не растут бесконтрольно |
| Размер WAL | `Get-ChildItem data\hackathon.db-wal` | единицы МБ; постоянный рост — признак зависшей транзакции |
| Фоновые задачи | `POST /api/v1/admin/jobs/run` | `locks_cleaned` и `overdue_notified` приходят без 500 |
| Уведомления | колокольчик в UI | новые просрочки появляются, мусора от песочницы нет |
| Docker (если используется) | `docker compose ps` | `Up`, при `unhealthy` — разбираться, не ждать |
| Туннель (если включён) | открыть публичный URL с мобильного интернета | вход и доска работают |

### 5.5. Чего нет в наблюдении

Метрик (Prometheus/`/metrics`), журнала фоновых задач, алертов, проверки целостности БД по расписанию, счётчиков ошибок. Ошибки планировщика не логируются. Неудачный бэкап обнаруживается только отсутствием свежей записи в списке. Всё это — ручные проверки из 5.4 и 9.

## 6. Публикация через fxTunnel

Статус: **не интегрировано**. `FXTUNNEL_TOKEN` читается в настройки и нигде не используется; клиента туннеля, службы, скрипта запуска и сервиса в compose нет. Никакой публикации «из коробки» не происходит. WebSocket в приложении тоже нет: UI опрашивает сервер (`/notifications` раз в 10 с, инциденты и аналитика раз в 5 с), поэтому туннелю достаточно обычного HTTP.

Что нужно понимать до включения:

| Аспект | Следствие |
| --- | --- |
| Что публиковать | Публикация только backend (`8000`) даёт API без UI: интерфейс в контейнер не входит и статикой не раздаётся. Публикация UI (`5173`) даёт единый origin, потому что Vite проксирует `/api` и `/health` на локальный backend |
| Проверка Host в Vite | Vite 5.4.21 проверяет заголовок `Host`. Внешний домен туннеля будет отклонён, пока он не добавлен в `server.allowedHosts` в `frontend/vite.config.ts`. Сейчас этого нет, то есть публикация UI требует правки конфигурации |
| Origin и CORS | CORS разрешает только `http://localhost:5173` и `http://127.0.0.1:5173` с credentials. Прямые запросы к API с другого домена браузер заблокирует; UI должен ходить через прокси того же origin |
| TLS | TLS завершается у провайдера туннеля: он видит расшифрованный трафик. Для открытого хакатонного проекта это принятый компромисс; конфиденциальные данные в систему не заводить |
| Cookie | Сессионная cookie ставится с `HttpOnly` и `SameSite=Lax`, но **без флага `Secure`**: она будет отправлена и по обычному HTTP. CSRF-токенов нет, защита — `SameSite=Lax` |
| Адрес | На бесплатном тарифе поддомен не резервируется и меняется после перезапуска туннеля; при смене домена пользователи теряют закладки и cookie (они привязаны к хосту), потребуется повторный вход |
| Тариф | Один активный туннель, HTTP(S); лимиты и условия проверять в актуальной документации провайдера — в коде и compose их нет |
| IP-адреса клиентов | Ограничение входа считает неудачи по IP из `request.client.host`. Если туннель подключается к приложению с localhost и не передаёт реальный IP, все внешние пользователи будут выглядеть как один адрес: 10 неудачных попыток за 15 минут заблокируют вход всей команде, а блокировка этого IP отрежет всех. Проверьте фактические IP в `Админ → Журнал входов` сразу после включения |

Порядок действий при включении (без изменений кода, кроме `vite.config.ts`, если публикуется UI):

1. Получить токен в личном кабинете провайдера, хранить его вне репозитория (в конфигурации клиента, не в `.env` проекта — приложение этот токен не читает).
2. Установить нативный клиент туннеля на ПК-сервер (Windows) по официальной документации; автозапуск — планировщиком Windows или службой, не systemd.
3. Решить, что публикуется: backend (`8000`) для API или UI (`5173`) для полноценной работы команды. Для людей нужен UI.
4. Для UI добавить домен туннеля в `server.allowedHosts` Vite и перезапустить `npm run dev`; без этого будет ответ «Blocked request».
5. Запустить туннель, получить HTTPS-адрес, открыть его с мобильного интернета (не из локальной сети), войти, проверить доску, таймер, загрузку документа.
6. Проверить журнал входов: IP должны различаться у разных людей; если все `127.0.0.1` — ограничение по IP фактически глобальное, временно отключите блокировку IP и полагайтесь на лимит по логину.
7. Перезапустить туннель и убедиться, что адрес изменился предсказуемо и команда оповещена; перед хакатоном повторить контрольный запуск.

Ограничения, которые нельзя обойти настройкой: нет CSRF-защиты, cookie без `Secure`, нет ограничения размера загрузок, нет блокировки по частоте API (только вход и ИИ), `/docs` открыт публично. Поэтому публикация допустима только на время хакатона и только с заранее выданными учётными данными.

## 7. Фоновые задачи

Планировщик — daemon-поток внутри процесса uvicorn, стартует в lifespan после миграций и bootstrap, останавливается по событию при завершении процесса.

| Задача | Периодичность | Что делает |
| --- | --- | --- |
| Очистка блокировок документов | каждый тик 60 с | удаляет `document_locks` с `last_activity_at` старше 5 минут (`LOCK_TTL`) |
| Уведомления о просрочках | каждый тик 60 с | по проектам не в состоянии `completed` находит задачи с `deadline < now`, не входящие в `done`/`realised`/`trashed`, и создаёт по одной нотификации `task_overdue` на задачу; получают все активные `participant`/`captain`/`admin` (не только исполнитель) |
| Автоматический бэкап | каждые 900 с | создаёт копию `automatic`, обновляет `latest.zip`, удаляет предыдущую обычную |

Чего в планировщике нет: ИИ по расписанию, отправки в Google Drive, уведомлений о приближении дедлайна проекта, очистки истёкших сессий и старых `login_events`, `VACUUM`, проверки целостности БД. Сбои задач глушатся и не логируются.

Ручной запуск (только задачи, без бэкапа):

- UI: `Админ → Резервные копии → Запустить фоновые задачи`;
- API: `POST /api/v1/admin/jobs/run` (капитан или админ).

Ответ: `{"locks_cleaned": N, "overdue_notified": M}`. Повторный запуск обычно даёт `0` по просрочкам (дедупликация по существующим `task_overdue`) и `0` по блокировкам (если никто не редактирует документы). Бэкап через эту кнопку не создаётся — только отдельной кнопкой.

Песочница и фоновые задачи: сценарий `overdue_as_dev` создаёт просроченную задачу в проекте `Sandbox`, и следующий тик рассылает о ней уведомления всей команде. После демонстраций чистите уведомления (`Очистить все`) или не запускайте такие сценарии во время хакатона.

## 8. Типовые инциденты и лечение

### 8.1. Вход, доступ, лимиты

| Симптом | Причина | Действие | Профилактика |
| --- | --- | --- | --- |
| `401 UNAUTHENTICATED` | нет cookie, сессия истекла (7 дней), отозвана, либо восстановлена БД без этой сессии | войти заново; при массовых 401 после восстановления — предупредить команду | не восстанавливать бэкап в разгар работы |
| `401 BAD_CREDENTIALS` | неверный логин/пароль, опечатка, раскладка | проверить логин в журнале входов; админ сбрасывает пароль | выдавать учётные данные заранее и проверять вход до старта |
| `403 DEACTIVATED` | пользователь деактивирован (роли и сессии отозваны) | активировать вручную через БД (см. 2.3), в API обратной операции нет | не деактивировать участников «на время» |
| `403 FORBIDDEN` | нет нужной роли (например, участник меняет время или бэкап) | выдать роль `captain`/`admin` | согласовать роли до хакатона |
| `403 IP_BLOCKED` | IP в чёрном списке | снять правило: `DELETE /api/v1/admin/ip-rules/{id}` (в UI кнопки нет) или `DELETE FROM ip_rules WHERE ip=...` при остановленном сервере | блокировать только после разбора журнала |
| `429 RATE_LIMITED` | 5 неудач на логин или 10 на IP за 15 минут | подождать 15 минут либо `Сбросить лимит` для IP (удаляет неудачные попытки) | не проверять пароли «наугад», проверять вход до старта |
| Все внешние пользователи блокируются одновременно | туннель скрывает реальные IP, лимит идёт по одному адресу | временно не блокировать IP, увеличить окно ожидания | проверить IP в журнале входов при включении туннеля |

### 8.2. Данные и конкурентный доступ

| Симптом | Причина | Действие | Профилактика |
| --- | --- | --- | --- |
| `409 VERSION_CONFLICT` при сохранении/перемещении задачи | задачу изменили в другой вкладке или другим пользователем; клиент прислал старую `version` | обновить список задач и повторить | одна вкладка на задачу, обновление перед правкой |
| `409 DOCUMENT_LOCKED` | документ редактирует другой пользователь, блокировка активна до 5 минут после последней активности | подождать до 5 минут; попросить закрыть редактор; принудительного снятия нет | не оставлять открытый редактор; heartbeat продлевает блокировку |
| `409 PROJECT_COMPLETED` | проект завершён голосованием | переоткрыть голосованием капитанов (`Настройки → Завершение хакатона`) | завершать проект только после финального бэкапа |
| `409 COLUMN_PROTECTED` | попытка удалить стартовую колонку | переименовать или использовать пользовательскую колонку | не удалять стартовые колонки |
| `409 LAST_ADMIN` | попытка деактивировать/разжать последнего админа | сначала выдать роль `admin` второму пользователю | держать двух админов |
| `500 database is locked` | конкурирующая запись, долгая транзакция, внешний инструмент (DB Browser), антивирус или синхронизация облака на `data/` | повторить операцию; закрыть внешние клиенты БД; проверить, что каталог не синхронизируется; при необходимости перезапустить сервер | не открывать рабочую БД сторонними инструментами; исключить `data/` из OneDrive/антивируса; таймаут SQLite — 30 с |
| Задача/время «не сохранились» | ошибка версии или откат после восстановления бэкапа | сверить часы и версию, посмотреть аудит | не восстанавливать бэкап без предупреждения команды |
| Пропали документы | восстановление заменило `documents/`; данные писались в другой `APP_DATA_DIR` (например, `backend/data`); скопировали только `hackathon.db` | проверить оба каталога и таблицу `documents`; вернуть каталог из бэкапа | держать один каталог данных, проверять путь через `settings.data_dir` |
| Документ есть в БД, но не открывается (`404 NOT_FOUND`) | файл удалён или каталог не скопирован | восстановить файл из бэкапа по пути `documents/<project_id>/<path>` | переносить `data/` целиком |
| `409 BACKUP_CORRUPT` | sha256 архива не совпал с записью: архив изменён, скопирован частично, повреждён диск/антивирус | взять другую копию; сверить хеш вручную; не править `checksum` в БД | копировать архивы только при остановленном сервере, хранить контрольные суммы, проверять восстановлением |

### 8.3. Инфраструктура

| Симптом | Причина | Действие | Профилактика |
| --- | --- | --- | --- |
| Не создаётся админ | в таблице `users` уже есть записи (например, после восстановления без админа); `APP_FIRST_ADMIN_*` меняли после первого старта | выдать роль через ORM-скрипт (2.3) или, если данные не нужны, удалить БД и перезапустить | не менять `.env` в расчёте на пересоздание админа; хранить доступ к БД |
| Время смещено | сбиты часы ПК; таймер оставлен запущенным на время простоя; дедлайн задан с неверным часовым поясом; смешаны бэкапы с разных машин | синхронизировать время (NTP), остановить таймеры, скорректировать время под капитаном (см. 10.1); сравнить `created_at` сущностей | включить синхронизацию времени; останавливать таймеры перед выключением ПК |

| Смешанный контент в браузере | UI открыт по HTTPS (туннель), а запросы идут на `http://127.0.0.1:8000` напрямую | использовать прокси Vite (относительные `/api`), не прописывать абсолютный HTTP-адрес | не менять базовый адрес API в клиенте |
| Порт 8000 занят | второй экземпляр uvicorn, другой сервис | найти процесс: `Get-NetTCPConnection -LocalPort 8000 -State Listen`; остановить или взять другой порт и поправить прокси | не запускать два экземпляра: они пишут в одну БД |
| Docker не видит данные | `.env` с относительными путями или удалённые override-переменные; том смонтирован из другого каталога; на Linux файлы принадлежат root | `docker compose exec app ls -la /data`; вернуть `APP_DATA_DIR=/data` и `DATABASE_URL=sqlite:////data/hackathon.db` в compose; `chown` каталога | не менять секцию `environment` в compose; помнить, что данные прямого запуска и Docker должны указывать на один каталог |
| Контейнер `unhealthy`, но работает | `/health` вернул 500 (БД недоступна) или таймаут | смотреть `docker compose logs app`, проверить путь к БД и права, перезапустить | healthcheck не лечит: нужен внешний монитор |
| `404` на проект после восстановления | в `localStorage` сохранён id проекта, которого нет в восстановленной БД | выбрать проект в выпадающем списке или очистить ключ `hcc-project` | предупреждать команду об откате |

## 9. Регламент обслуживания

### 9.1. Ежедневно (во время хакатона)

- `/health` — 200; UI открывается, вход работает.
- Последний бэкап моложе 20 минут; если старше — создать вручную.
- Свободное место на диске с `data/` (минимум 1 ГБ) и размер `-wal`.
- Журнал входов: нет ли серии отказов и заблокированных IP.
- Запущенные таймеры соответствуют реальной работе (нет «забытых» с прошлого дня).
- Уведомления о просрочках доходят, мусора от песочницы нет.

### 9.2. Еженедельно

- Ручной бэкап + копия `latest.zip` на другой носитель (флешка, сетевой диск).
- Проверка `integrity_check` и восстановление на копии данных (не на рабочих).
- Чистка старых `*_safety.zip`, контроль роста `data/`.
- Ревизия пользователей и ролей: деактивировать ушедших, проверить, что админов не меньше двух.
- Проверить, что `.env` не попал в git и в архив с данными.

### 9.3. Перед хакатоном

1. Сменить пароль админа с `change-me`, создать учётные данные участникам и капитанам, проверить вход каждым.
2. Проверить `.env`: абсолютные пути или отсутствие `APP_DATA_DIR`/`DATABASE_URL`; секреты не в репозитории.
3. Пробный запуск выбранного режима (прямой или Docker), миграции применяются без ошибок.
4. Сделать ручной бэкап и один раз пройти восстановление на копии данных.
5. Синхронизировать время на ПК, включить автозапуск Docker Desktop или подготовить ручной старт.
6. Если используется туннель — включить, проверить HTTPS и вход с мобильного интернета, записать адрес для команды, проверить реальные IP в журнале входов.
7. Убедиться, что на диске с `data/` есть запас места, а каталог исключён из облачной синхронизации и антивирусного сканирования.
8. Очистить уведомления и тестовые задачи, проверить, что проект в нужном состоянии (`preparation`).

### 9.4. После хакатона

1. Финальный ручной бэкап и копия архива за пределы ПК.
2. Завершить проект голосованием капитанов (`completed`) — рабочие сущности станут read-only.
3. Деактивировать временных пользователей и участников песочницы (`alice`, `bob`, `cap`), отозвать лишние роли.
4. Остановить туннель, отозвать/удалить токен, если он больше не нужен.
5. Сохранить `.env` отдельно от данных (он не входит в бэкап).
6. Зафиксировать, какая версия кода работала (commit), и не обновлять её до архивирования.

- [ ] Пароль первого админа изменён; `change-me` нигде не используется.

## 10. Аварийное восстановление

### 10.1. Таймеры после простоя

| Аспект | Факт |
| --- | --- |
| Состояние при падении/выключении | `TaskTimer.state` остаётся `running`, `last_started_at` сохранён; открытый `TimerSegment` не закрывается |
| Как считается время после старта | `elapsed = now - last_started_at`, то есть весь простой ПК засчитывается как работа; в отчётах открытый сегмент учитывается до текущего момента |
| Автокоррекция | отсутствует: сверки интервалов с реальным временем и фоновой корректировки нет |
| Что делать | после старта остановить все «висящие» таймеры, затем капитан/админ выставляет фактическое время через корректировку (`POST /api/v1/tasks/{id}/time-adjustment`, `accumulated_seconds`) |

Порядок корректировки: сначала `stop` таймера (иначе корректировка меняет только `accumulated_seconds`, а идущее время продолжит добавляться), затем `time-adjustment`, затем сверка итога в аналитике. Корректировка пишется в аудит (`task.time_adjusted`). Массово найти запущенные таймеры можно в аналитике (счётчик активных таймеров) или запросом к БД при остановленном сервере:

```powershell
..\.venv\Scripts\python.exe -c "import sqlite3; db=sqlite3.connect(r'data\hackathon.db'); print(db.execute(\"select task_id, state, last_started_at from task_timers where state='running'\").fetchall())"
```

### 10.2. WAL

- В рабочем режиме рядом с `hackathon.db` есть `-wal` (незакоммиченные в основной файл страницы) и `-shm`. Это часть базы, а не мусор.
- Нельзя копировать только `hackathon.db` при работающем сервере: последние транзакции останутся в `-wal` и потеряются. Для копирования используйте бэкап-эндпоинт (SQLite backup API) или останавливайте сервер.
- Не удаляйте `-wal`/`-shm` вручную при работающем сервере — это повреждение данных.
- После аварийного завершения SQLite восстанавливается сам при следующем открытии: не «лечите» файлы, просто запустите сервер.
- Постоянно растущий `-wal` — признак долгой читающей транзакции или зависшего процесса; перезапуск сервера сворачивает WAL.

### 10.3. Повреждение БД

Признаки: `database disk image is malformed`, `file is not a database`, ошибки чтения при старте, `/health` стабильно 500.

```powershell
# сервер остановлен
Copy-Item data data.broken -Recurse
..\.venv\Scripts\python.exe -c "import sqlite3; db=sqlite3.connect(r'data\hackathon.db'); print(db.execute('pragma integrity_check').fetchall()[:5])"
```

Действия по возрастанию потерь:

1. `integrity_check` вернул `ok` — проблема не в файле: проверьте путь из `.env`, права на каталог, свободное место, блокировки антивирусом.
2. Есть свежий бэкап — восстановите его по 3.6 (вручную) и проверьте документы. Потеря — всё, что сделано после копии (до 15 минут при работающем планировщике плюс время с последней успешной копии).
3. Бэкапа нет, но файл открывается и часть таблиц читается — выгрузите доступное (как минимум `documents/` на диске целы) и заведите новую БД; не пытайтесь «дочинить» рабочую копию, работайте с копией `data.broken`.
4. Ничего не помогает — переименуйте `hackathon.db` в `hackathon.db.corrupt`, запустите сервер: создастся пустая БД с админом и проектом. Документы на диске останутся, но без записей в БД они не видны — их можно импортировать заново вручную.

### 10.4. Когда откатываться на бэкап

| Откатываться | Не откатываться |
| --- | --- |
| БД повреждена или не открывается | единичная ошибка 409/422 у пользователя |
| Массовое удаление/порча данных (ошибочная правка, сбой скрипта) | «не сохранилась одна задача» — сначала разобраться по аудиту |
| Неудачное обновление кода/миграция, после которой приложение не стартует | UI-глюк, который лечится перезагрузкой страницы |
| Потеря ПК и перенос на другой (откат = восстановление последней копии на новом ПК) | истёкшая сессия или забытый пароль |

Правило: перед откатом сохраните текущее состояние (копия каталога `data/` или ручной бэкап), даже если оно кажется испорченным — это единственный источник данных, созданных после последней копии.

### 10.5. Полный порядок аварийного восстановления

1. Остановить сервер (не оставлять два процесса на одной БД).
2. Скопировать весь каталог `data/` в `data.broken` (страховка).
3. Проверить `integrity_check`; при повреждении — перейти к восстановлению из архива.
4. Развернуть код нужной версии (тот же commit, что работал), создать venv, `pip install`.
5. Восстановить БД и `documents/` из `latest.zip` (3.6), проверить `integrity_check` на восстановленном файле.
6. Запустить сервер, дождаться миграций, проверить `/health`, вход, число задач и документов.
7. Остановить «висящие» таймеры и скорректировать время (10.1).
8. Сделать новый ручной бэкап и убедиться, что он в списке.
9. Сообщить команде: какие данные потеряны (окно между копией и аварией), что входы могли сброситься, что адрес туннеля мог измениться.

## Расхождения и ограничения

Проверено по коду; влияет на эксплуатацию.

| № | Ожидание (README, `docs/03`, `.env.example`) | Фактически | Влияние |
| --- | --- | --- | --- |
| 1 | Docker и прямой запуск используют одну папку `data/` и одну БД | `APP_DATA_DIR=./data` и `DATABASE_URL=sqlite:///./data/...` из `.env.example` относительны CWD, а backend запускается из `backend/` → данные уходят в `backend/data/` | «Пропали данные», расхождение режимов; лечится удалением этих строк из `.env` |
| 2 | `/health` проверяет БД и запись в каталог данных | Выполняется только `SELECT 1`; каталог, миграции и место на диске не проверяются; ошибка БД даёт 500 без конверта ошибки | Зелёный health при нерабочих документах/бэкапах |
| 3 | Docker-режим даёт работающий штаб | В образ входит только backend; UI нужно запускать отдельно (Node на хосте); статика не раздаётся | Docker сам по себе даёт только API |
| 4 | Прямой запуск на Linux | `start.sh` использует `.venv/Scripts/python.exe` (Windows-путь) и на Linux не работает | Ручной запуск uvicorn |
| 5 | Autoheal и Uptime Kuma контролируют зависания | Не реализованы: нет контейнеров, меток, алертов; `restart: unless-stopped` не реагирует на `unhealthy` | Нет автоматического перезапуска и оповещений |
| 6 | fxTunnel публикует приложение | `FXTUNNEL_TOKEN` читается и не используется; клиента, службы и инструкций запуска нет | Публикация только вручную и только после правки `allowedHosts` Vite |
| 7 | Telegram работает как mock до передачи токена | Отправки нет при любых значениях; лог-строка на уровне INFO, а корневой логгер не настроен | Уведомления только внутри приложения; в логах их не видно |
| 8 | `.env` управляет портом и секретом приложения | `APP_HOST`/`APP_PORT` нигде не читаются (порт задан в скриптах и Dockerfile), `APP_SECRET_KEY` не используется | Смена порта в `.env` ничего не меняет |
| 9 | Пользователь может сменить свой пароль | Самостоятельной смены нет; только сброс админом | Нужен админ или правка БД |
| 10 | Деактивацию можно отменить | Обратной операции нет (нет API/UI «активировать»), только правка БД | Ошибочная деактивация требует вмешательства |
| 11 | `participant`/`captain` привязаны к проекту | UI назначает роли с `project_id = NULL`, проверки прав проект не учитывают; список проектов доступен любому аутентифицированному | Изоляции проектов нет: участник видит и меняет данные любого проекта |
| 12 | Завершённый проект полностью read-only | `409 PROJECT_COMPLETED` только для задач, таймеров и инцидентов; документы, колонки, модули, название и дедлайн меняются | «Зафиксировать» проект полностью нельзя |
| 13 | Восстановление совместимо с любой копией | Вместо миграций выполняется `alembic stamp head`; запись о копии не попадает в её же архив; `safety`-копия после восстановления не видна в списке | Копии от другой версии ломают схему; история копий после отката неполная |
| 14 | Одна последняя копия, бэкап каждые 10–15 минут | Обычная копия действительно одна, но `safety`-копии копятся без ограничения; отсчёт 900 с начинается заново при каждом старте | При частых перезапусках автобэкапов нет; диск забивается |
| 15 | Внешняя копия (Google Drive) | Не реализована | Единственная копия — на том же диске |
| 16 | После восстановления таймеры сверяются с фактическим временем | Автокоррекции нет: простой засчитывается как работа | Ручная корректировка капитаном (10.1) |
| 17 | Песочница изолирована от рабочих данных | Создаёт реальных пользователей с паролем `sandbox-pass` и ролями; просроченные задачи песочницы попадают в уведомления команды | Учётные записи и шум в уведомлениях; деактивировать после демо |
| 18 | Фоновые задачи наблюдаемы | Исключения глушатся без логов; метрик и журнала задач нет | Сбой бэкапа/задач виден только по косвенным признакам |
| 19 | Состояние `active` используется в работе | Перевести проект в `active` через UI/API нельзя (только `preparation` → `completed` → `preparation`); `active` есть только у проекта песочницы | Состояние в интерфейсе почти всегда `preparation` |
| 20 | Защита сессий соответствует требованиям | Cookie без `Secure`, CSRF-токенов нет, лимит частоты только на вход и ИИ, `/docs` открыт, размеры загрузок не ограничены | Принятые ограничения прототипа; учитывать при публикации |
