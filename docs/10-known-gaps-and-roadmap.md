# Пробелы, техдолг и план развития

Документ фиксирует разницу между текущим прототипом и требованиями из [docs/](README.md), а также технические риски, которые нужно учитывать при развитии. Он не заменяет [07-implementation-status.md](07-implementation-status.md): там — что уже работает, здесь — чего не хватает и в каком порядке это делать.

Приоритеты:

- **P0** — блокирует заявленный сценарий использования или создаёт риск потери данных/утечки.
- **P1** — заметно влияет на эксплуатацию, но обходится вручную.
- **P2** — улучшение качества и удобства.

## Сводка

| P0 | 6 | UI документов, реальный Telegram, проектная изоляция прав, путь к данным из `.env.example`, проверка записи в `/health`, отсутствие UI для восстановления/аудита |

GAP-05 стоит закрыть первым: он не требует кода, достаточно привести пример конфигурации к абсолютному пути или запускать сервер из корня и явно это описать. Сейчас корректная работа с корневой `data/` держится на дефолте `PROJECT_ROOT/data` в `backend/app/config.py`, который перекрывается примером `.env`.

## P1. Эксплуатация и безопасность

| ID | Область | Пробел | Влияние |
| --- | --- | --- | --- |
| GAP-07 | Сессии | Cookie без флага `Secure`, нет CSRF-токена; `APP_SECRET_KEY` не используется | При публикации через туннель выше риск перехвата/подделки запросов; секрет в `.env` создаёт ложное чувство защиты |
| GAP-08 | Реальное время | WebSocket отсутствует; доска опрашивает API раз в 1 с, инциденты и аналитика — раз в 5 с, уведомления — раз в 10 с | Нагрузка и задержки; при нескольких открытых вкладках трафик растёт линейно |
| GAP-09 | ИИ | Провайдеры Gemini/DeepSeek не подключены (`_mock_recommendation`), `excluded` не влияет на снимок, триггеры не используются планировщиком, лимит хранится в памяти процесса | Функция демонстрационная; после перезапуска лимит сбрасывается, при нескольких воркерах не работает |
| GAP-10 | Docker | Образ содержит только backend; frontend не собирается и не раздаётся, `docker compose` поднимает API без UI | Docker-режим не даёт готовый штаб «одной командой» |
| GAP-11 | Мониторинг | Нет Autoheal, Uptime Kuma, алертов о перезапусках; в compose только `restart: unless-stopped` и healthcheck | Зависание процесса не лечится автоматически, команда узнаёт о сбое от пользователей |
| GAP-12 | fxTunnel | Интеграция отсутствует, есть только `FXTUNNEL_TOKEN` в конфиге | Нет публичного HTTPS-адреса из коробки |
| GAP-13 | Google Drive | Переменная `GOOGLE_DRIVE_FOLDER_ID` не используется | Нет внешней копии бэкапа, требования docs/03 не выполнены |
| GAP-14 | Загрузки | Нет ограничения размера и количества изображений, SVG принимается как есть | Риск заполнения диска и XSS через SVG при будущем рендере |
| GAP-15 | Восстановление | Бэкап восстанавливается «на живом» процессе: соединения закрываются, engine пересоздаётся, но сервер не перезапускается и активные сессии не инвалидируются | Возможны ошибки у пользователей с открытыми вкладками; нужен регламент перезапуска |

## Технический долг

1. **Планировщик в одном процессе.** Поток создаётся в `lifespan`; при `uvicorn --workers N` каждая реплика запустит свои задачи и бэкапы. Нужен либо явный запрет нескольких воркеров в документации и конфигурации, либо блокировка/лидерство.
2. **Аудит неполон.** Часть мутаций не пишет записи: настройки ИИ, бэкапы, восстановление, правки чек-листа, работа с уведомлениями. При этом журнал можно редактировать (`PATCH /admin/audit/{id}`) с сохранением ревизий.
3. **Денормализация `Module.traffic_status`.** Поле хранится, но реальный светофор вычисляется из инцидентов и не синхронизируется с колонкой; значения в БД могут расходиться с отображением.
4. **Смешение «глобальных» и «проектных» ролей.** API принимает `project_id=None` для `participant`/`captain`; фронтенд так и делает. Фактически роли глобальные, хотя модель допускает проектную привязку.
5. **Версионирование задач частично.** `version` растёт при `PATCH`, `move`, смене исполнителей, но не при изменении зависимостей и чек-листа — конфликты по этим полям не ловятся.
6. **Дублирование снимков.** `dashboard` и `analytics.kpi` считают почти одно и то же разными функциями; расхождения возможны при изменении правил.
7. **Ошибки глотаются.** Фоновый цикл ловит `Exception` без логирования; при сбое бэкапа не остаётся следа, кроме отсутствия файла.
8. **Относительные пути.** `APP_DATA_DIR` и `DATABASE_URL` разрешаются от текущего каталога процесса; документация и скрипты должны это явно фиксировать (см. GAP-05).
9. **`TaskOut` собирается вручную.** Сериализация задачи в `services/tasks.py` дублирует поля модели; новое поле нужно добавлять в трёх местах (модель, схема, сериализатор).
10. **Тестовая БД переиспользуется.** `backend/tests/conftest.py` держит общий `tests/.tmp/test.db` и делает `drop_all/create_all` на каждый тест; тесты нельзя запускать параллельно, а `.tmp` попадает в рабочее дерево.

## План развития

### Итерация 1. Стабилизация (1–2 дня)

1. GAP-05: исправить пример конфигурации и инструкции запуска, чтобы данные всегда лежали в корневой `data/`.
2. GAP-06: расширить `/health` проверкой записи в папку данных; добавить тест.
3. GAP-04: проверять принадлежность проекта и роль в проекте для задач, документов, инцидентов; добавить тесты на доступ к чужому проекту.
4. GAP-02: экран аудита с фильтрами по проекту/актору/действию (API уже есть).
5. GAP-15: задокументировать обязательный перезапуск после восстановления; рассмотреть инвалидацию сессий.

### Итерация 2. Полнота функций (3–5 дней)

1. GAP-01: экран Markdown-документов: дерево, редактор, preview, изображения, блокировки, корзина (бэкенд готов).
2. GAP-03: реальная отправка в Telegram + журнал доставки и повтор при ошибке.
3. GAP-10: сборка фронтенда и раздача статики из FastAPI/Docker.
4. GAP-09: подключение Gemini/DeepSeek за общим интерфейсом провайдера, сохранение лимита в БД, учёт `excluded`.
5. GAP-18/19: редактирование свойств задачи, порядок колонок, удаление задач.

### Итерация 3. Эксплуатация (3–5 дней)

1. GAP-11: `autoheal` и Uptime Kuma в compose, инструкция и проверка тестовым падением.
2. GAP-12: запуск fxTunnel, документирование TLS-компромисса и смены адреса.
3. GAP-13: выгрузка бэкапа в Google Drive с ограниченными ретраями.
4. GAP-07: `Secure`-cookie при HTTPS, CSRF-токен для мутаций.
5. GAP-17: e2e-тесты Playwright на вход, доску, таймер, инцидент, документ.

### Итерация 4. Развитие (по запросу)

Экспорт и отчёты, архив проектов, мобильная вёрстка, несколько проектов на одном экране, интеграция с внешними трекерами — только после закрытия P0/P1 и появления реальной потребности.

## Критерии готовности следующей вехи

- Все P0 закрыты и покрыты тестами (для UI — e2e или ручным чек-листом в runbook).
- `docs/07-implementation-status.md` не содержит статуса «не реализовано» для обязательных требований docs/02.
- `docker compose up --build` даёт работающий UI и API на одном адресе.
- Бэкап и восстановление проверены на копии реальных данных, описан регламент перезапуска.
- Нет расхождений между `specifications/*` и кодом (проверяется при ревью изменений).

## Как обновлять документ

- Пробел закрыт — перенесите строку в [07-implementation-status.md](07-implementation-status.md) как «реализовано» и удалите её отсюда.
- Появился новый пробел — добавьте строку с ID, областью, влиянием и ссылкой на требование.
- Не храните здесь задачи без приоритета: если непонятно, P0 это или P2, значит требование ещё не сформулировано.
