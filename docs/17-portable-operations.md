# Переносимая поставка и локальное управление

Состояние на 29 октября 2026: реализован локальный менеджер платформ на pywebview для Windows + WSL 2 + Ubuntu 24.04 + Docker Engine. Пользователь подтвердил работу туннеля и отправку оповещений/архивов Telegram. Полная приёмка отдельной Linux-машины **не завершена**. Испытания с изменением данных выполняются только в `.tmp`; рабочая база проверялась на чтение для определения действующих данных входа, без сброса паролей.

## Запуск и устройство

1. Windows: Python 3.12+, `start.bat` или `start.ps1`. Linux: Python 3.12+ с модулем venv, `bash start.sh`. Окружения панели раздельные: `.control/venv-windows`, `.control/venv-linux`. Разработка сохраняется в `start.ps1 -Development`.
2. Хаб открывается отдельным окном pywebview; браузер для управления не требуется. Внутренний API слушает только `127.0.0.1:8787`. Случайная capability передаётся во фрагменте локального URL, удаляется и обменивается на HttpOnly/SameSite=Strict cookie. Изменения требуют точный Origin; Host ограничен loopback. Крестик сворачивает окно в трей; повторный запуск показывает существующее окно. «Остановить платформу» оставляет хаб работающим. «Выключить хаб» в настройках или трее останавливает платформу и туннель, затем завершает приложение.
3. Мастер проверяет зависимости и предлагает следующий шаг установки. После UAC/перезагрузки проверка повторяется, новые изменения требуют нового нажатия. Автоустановка Docker предусмотрена для Ubuntu 22.04/24.04 из официального подписанного APT-репозитория. Конфликтующие пакеты не удаляются. Для существующего Docker без Compose показан ручной шаг установки plugin; полная автоматизация этого случая пока отсутствует.
4. Windows использует `Ubuntu-24.04` по имени, без изменения дистрибутива по умолчанию или общих лимитов WSL. Перед использованием иной уже существующей WSL-среды нужна явная настройка дистрибутива; автоматический выбор среди нескольких движков пока отсутствует. Панель удерживает собственный клиент WSL с открытым stdin: systemd сам не удерживает WSL работающим. При завершении панели EOF завершает этот клиент. Глобальный `instanceIdleTimeout` не меняется.
5. На вкладке настроек создайте платформу в пустой папке либо запустите сохранённую. Установки имеют отдельные БД, документы, настройки и ключи. Переключение останавливает предыдущую, выбранная запоминается как основная. Автозапуск ОС поднимает основную и прячет хаб в трей. Старый одиночный профиль автоматически включается в список без переноса данных. Пароли существующих пользователей не меняются; новый оператор получает случайный пароль и глобальную роль администратора, без автоматического проекта.
6. «Собрать образ» собирает frontend через npm ci и backend по `backend/requirements.lock`. Базовые образы закреплены digest. «Старт» запускает отдельный Compose-проект `hcc-<id>`; порт платформы — `127.0.0.1:8000`. Секреты, `.env`, данные, окружения и архивы исключены из build context. Frontend dev server не используется.

Образы и постоянные данные различаются. Сохранение архива не сохраняет Docker-образ. Для передачи без доступа к registry можно отдельно выполнить `docker save hcc-platform:0.2.0` и затем `docker load` на целевом движке. Архив требует **точно совместимую поставку**; версия архива проверяется.

## Ключи

Windows: DPAPI текущего пользователя; Linux: AES-GCM/Scrypt и отдельная фраза хранилища от 16 символов. Фразу Linux нужно вводить после запуска панели; автоматический запуск контейнера до разблокировки не обещается. Секреты материализуются только в защищённой runtime-папке для read-only монтирования контейнеру; в Windows это `/run/hcc-<id>` внутри WSL. Они не передаются в аргументах команд, Compose-конфигурации или образе. Linux runtime-файлы ограничены правами владельца, но не являются аппаратным хранилищем.

Показ ключа — отдельное локальное POST-действие. Первоначальный пароль новой установки совпадает с ключом архивов. Изменение пароля аккаунта в платформе **не меняет** ключ архивов. При восстановлении с другим ключом прежний ключ сохраняется в зашифрованной истории и выбирается в окне показа ключа. Сохраните ключ вне исходного компьютера. Отдельная ротация ключа через панель пока не реализована.

При подключении старых данных ключ панели шифрует новые архивы, но не заменяет существующий пароль администратора. Старые DPAPI-хранилища Gemini/Telegram не импортируются автоматически; интеграционные секреты вводятся локально заново. Не передавайте их в чат.

Окно доступа разделяет логин/пароль входа и ключ архивов. Для существующей БД известные локальные пароли (начальный пароль, ключи и старый APP_FIRST_ADMIN_PASSWORD) сверяются по bcrypt-хешу активного глобального администратора. Отображается только подходящая пара. Если подходящего пароля нет, хаб сообщает, что пароль неизвестен; автоматического сброса нет. Секретные поля очищаются при закрытии окна доступа и переключении установки.

После запуска платформы и готовности API хаб автоматически открывает fxTunnel, если его секрет сохранён. Поддомен по умолчанию — `dots-bots-hub`; явно заданный другой поддомен сохраняется. Если домен занят или тариф его не поддерживает, потребуется другой домен. Кнопка «Открыть платформу» использует только проверенную ссылку туннеля и недоступна до её получения.

Telegram использует одного бота и два независимых направления (чат и необязательная тема): архивы и оповещения. Каждая замеченная смена статуса попадает в сохраняемую очередь; сообщения содержат упоминание администратора, название платформы, время и цветной статус. HTML-разметка экранирует внешний текст. Ответы API различают неверный токен, чат, тему и недостаточные права; сетевой обрыв отмечается как неопределённый результат. После неудачной доставки копии повтор разрешён через 30 секунд; успешные автоматические отправки ограничены интервалом 30 минут.

## Согласованность, копии и перенос

- В управляемом приложении один процесс держит `.server.lock`. Изменяющие HTTP-запросы, планировщики и maintenance worker используют общий файловый барьер. Worker снимка не запускает FastAPI и планировщики. Старое автоматическое резервирование на 15 минут отключено. Старые API создания/восстановления ZIP требуют использовать локальную панель.
- Каждые 5 минут панель получает SQLite online backup и документы под этим барьером. Проверяются SQLite integrity/FK, схема и SHA-256 файлов. Сравнивается содержимое снимка; служебные heartbeat/состояния панели и предыдущие архивы не входят в fingerprint. Без изменений новый автоматический архив не создаётся. Ручное создание делает новый полный архив.
- Формат `.hcc`: AES-256-GCM, Scrypt с отдельной случайной солью и nonce; манифест и содержимое аутентифицированы вместе. Публикация — через временный файл и атомарную замену. Предел MVP: 512 МиБ распакованного содержимого и 10000 файлов. Это ограничение реализации, а не обещание приемлемого потребления памяти при предельном размере.
- Локальная история: все копии за сутки, затем до семи ежедневных. Очистка ограничена записями и именами текущей установки. Последняя пригодная копия сохраняется. Дополнительная папка необязательна; при возвращении диска передаётся актуальная копия, а не очередь пропусков. Существующие посторонние файлы не удаляются.
- Telegram использует только outbound `sendDocument`, без второго getUpdates. Первая новая копия отправляется сразу; затем не чаще раза в 30 минут, включая задержку повторной попытки. После неопределённого ответа повтор может создать дубликат — это явно показывается. Отправляется только зашифрованный файл, без звука и упоминаний, с датой UTC, версией и размером. Облачный лимит — 50 МБ; превышение отображается отдельно и не отменяет локальную копию. Ручная отправка также соблюдает интервал. Архивы в Telegram автоматически не удаляются.
- Восстановление: файл → ключ → проверка → просмотр состава → отдельное подтверждение. Архив содержит **все проекты и аккаунты**. Проверяются пути, отсутствие ссылок/дубликатов/лишних файлов, размеры, версия и схема. Платформа останавливается; до замены создаётся зашифрованная защитная копия. Замена базы, WAL/SHM и документов имеет откат при ошибке. Автоматическое исправление версии Alembic не применяется.
- После восстановления старые Telegram pending/sending помечаются uncertain, незавершённые AI-задания — failed, автоматический ИИ выключается, сессии отзываются. Работавшие таймеры приостанавливаются на времени снимка, а не продолжают учитывать время выключенного сервера. Аккаунты и их хеши паролей сохраняются.
- Требуется подтверждение остановки прежнего сервера. До него новая платформа не запускается. ИИ дополнительно блокируется на 24 часа, затем требует включения в настройках проекта. Это консервативная пауза, а не синхронизация квоты с провайдером. Две изолированные установки технически не могут автоматически обнаружить друг друга.

Переносимые настройки проектов хранятся в БД. Локальные пути, направления общих резервных копий и конфигурацию панели на новом компьютере нужно настроить отдельно; они пока не входят в архив.

## Сеть, восстановление и диагностика

Перед плановой отправкой Telegram панель дополнительно проверяет свежие изменения, чтобы несовпадение фаз пятиминутных копий и получасовой отправки не добавляло устаревание. При ошибке обновления отправляется последняя проверенная копия с её настоящей датой и отдельным предупреждением.

fxTunnel запускается отдельным дочерним официальным CLI на хосте; требуется предварительная установка клиента. Секрет передаётся в окружении дочернего процесса, инспектор принудительно выключен. Публикуется только платформа на порту 8000. Переподключение CLI ограничено пятью попытками. В панели показывается только проверенная HTTPS-ссылка: проверяется установка, frontend и отказ в анонимном `/auth/me`. Требуется реальная проверка установленной версии CLI: JSON как YAML-конфигурация и разбор выданного URL ещё не проверены с живым провайдером.

Новые проектные Telegram-уведомления используют проверенный адрес с TTL 60 секунд вместо старого URL настроек. Уже сформированные сообщения в очереди могут содержать прежнюю ссылку: переработка таких сообщений перед отправкой пока не выполнена. Полная проверка SSE через публичный туннель и доверенной цепочки клиентского IP также остаётся до выпуска. Непроверенные X-Forwarded-For не принимаются. Для общего адреса туннеля ошибки входа считаются по логину, чтобы один нарушитель не заблокировал всех.

Docker отвечает за завершившиеся контейнеры (`on-failure:3`); панель — за нездоровый работающий API с паузами, grace period 90 секунд и пределом 3 попытки. Явная остановка через панель сохраняет desired=false до остановки контейнера. Возврат движка и запуск панели учитывают сохранённое желание оператора. Миграции и проблемы хранилища не лечатся перезапуском; автоматического отката БД нет. Причина миграции отражается в `.startup-state.json`; сырые журналы провайдеров в диагностический экспорт не попадают.

Автозапуск включается отдельным действием: Windows HKCU Run после входа; Linux desktop autostart после графического входа. Headless systemd-служба Linux пока не реализована. Сон и питание не меняются. Метрики хоста, панели и контейнера различаются; недоступное значение показывается прочерком. Общая память/CPU WSL и dockerd отдельными метриками пока не представлены. Состояния имеют время проверки; история CPU ограничена последними 60 замерами.

## До полной приёмки

Пользователь подтвердил живые Telegram и fxTunnel. Новое оформление сообщений и автоматическое открытие туннеля после готовности API проверены автоматическими тестами; повторные реальные отправки во время исправлений не выполнялись.

Также остаются: реальные падение/зависание приложения и перезапуск всего Docker; повтор мастера после перезагрузки/UAC/отказа прав; физическое отключение диска; крупная БД и параллельные записи под нагрузкой; полные замеры WSL + dockerd + панель + платформа в покое/при backup; отдельная чистая Linux-машина и Linux с существующим Docker; реальный вход после автозапуска ОС; живой туннель/SSE/cookies/IP. Эти сценарии нельзя считать пройденными по unit-тестам.

Источники установки и ограничений: [Docker Ubuntu](https://docs.docker.com/engine/install/ubuntu/), [команды WSL](https://learn.microsoft.com/windows/wsl/basic-commands), [жизненный цикл systemd/WSL](https://learn.microsoft.com/windows/wsl/systemd/), [Telegram sendDocument](https://core.telegram.org/bots/api#senddocument), [fxTunnel config](https://fxtun.ru/docs/config), [выключение инспектора](https://fxtun.ru/docs/inspector).

## Ouroboros Daemon и проекты Aion

Ouroboros Daemon управляет изолированными проектами; Aion работает только с выбранным проектом.
Agora — доска, Chronos — планирование, Argus — ИИ, Hermes — доставка оповещений.
Новая установка сразу создаёт проект и стартового администратора.
Внутри управляемого Aion нельзя создавать второй проект или запускать многопроектную песочницу.

Для старой базы выберите «Разделить старую базу на проекты». Исходная папка остаётся нетронутой;
копии получают независимые аккаунты с прежними паролями и документы только своего проекта.
После разделения настройте ключи отдельно и завершите активацию переноса в панели.
Очереди внешних действий приостановлены, автоанализ выключен; применяется защитная пауза ИИ.
При ошибке неопубликованные копии могут остаться на диске, исходная установка сохраняется.

Telegram/Gemini/fxTunnel задаются, заменяются и удаляются исключительно в Ouroboros Daemon.
Пустые поля сохраняют ключ; флажок удаления очищает его. Для Telegram/Gemini требуется перезапуск Aion.
Чаты, темы и частота ИИ меняются внутри Aion; аварийные чаты и архивы — в Ouroboros Daemon.

## Удаление проектов

В списке проектов Ouroboros Daemon выберите проект и нажмите «Удалить проект…».
Для подтверждения введите его точное название. Без дополнительного флажка проект
убирается только из списка: папку с данными можно подключить снова.

Флажок «Также безвозвратно удалить данные, ключи и локальные копии проекта» удаляет
папку данных и локальное состояние проекта. Сначала останавливаются контейнер и туннель,
удаляются контейнер и временные секреты. Общий Docker-образ сохраняется.
Внешние архивы и файлы в Telegram остаются. Другой проект автоматически не запускается;
можно удалить и последний проект, затем создать новый. Папки приложения, других проектов,
исходные базы после разделения и папки со ссылками защищены от удаления.

Runtime-папки, архивы и node_modules исключены из Git и Docker build context.
В новых папках данных создаётся локальный .gitignore, чтобы защитить также произвольные имена.
