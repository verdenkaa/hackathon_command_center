# Стабилизация прототипа · 2026-10-27

## Согласованный объём

- Аккаунты общие для всех проектов. Администратор — глобальная роль; участник и капитан назначаются отдельно для каждого проекта.
- Экран документов, редактор Markdown, предпросмотр и файловое дерево исключены из продукта и дальнейшего плана. Существующие API и файлы сохраняются для совместимости.
- ИИ и Telegram работают только как моки. Наличие ключей не включает внешние вызовы. Реальные интеграции будут отдельным этапом после проверки через UI.

## Права и данные

`require_role` учитывает проект URL или владельца объекта (задача, колонка, модуль, чек-лист, документ, инцидент). Общий аккаунт видит только назначенные проекты. Капитан одного проекта не получает права капитана в другом. Глобальный администратор имеет доступ ко всем проектам.

API назначения роли требует `project_id` для участника и капитана. UI «Админ → Пользователи» назначает и показывает эти роли для выбранного проекта. Повторная выдача отозванной роли разрешена; выдача активной роли возвращает `ROLE_EXISTS`.

Миграция `20261027_project_roles_mock` сохраняет старый доступ: общие назначения участника/капитана разворачиваются в роли для всех существовавших на момент обновления проектов, исходные назначения отзываются. На новые проекты такой доступ не распространяется. Миграция не удаляет пользователей, задачи, инциденты или файлы.

Списки и метрики участников, светофор, получатели уведомлений и голосование за завершение ограничены проектом. Назначить исполнителем или целью инцидента постороннего пользователя нельзя. Изменения завершённого проекта запрещены, кроме голосования за повторное открытие.

## Проверка ИИ

1. Выбрать тестовый проект, открыть «Настройки → ИИ-советник».
2. Включить мок, изменить промпт, условный провайдер, интервал и события.
3. В «Аналитике» задать вопрос или дополнительный контекст и выбрать причину запуска.
4. «Показать контекст запроса» показывает `mode`, `provider`, `prompt`, `trigger`, `question`, `snapshot`. Для предпросмотра не требуется включать ИИ, история не меняется.
5. «Запросить мок-анализ» сохраняет рекомендацию и исходный запрос. Ответ формируется по фиксированным правилам; промпт и вопрос не интерпретируются настоящей моделью.
6. Капитан или администратор может исключать прошлые рекомендации из следующего контекста и возвращать их обратно.

Снимок содержит задачи выбранного проекта (без корзины), описания, статусы, приоритеты, теги, оценки, дедлайны, ID исполнителей, активные инциденты и до пяти прошлых рекомендаций, не исключённых из контекста. Пароли, сессии, ключи и документы в снимок не входят.

Включённые события блокеров и эскалаций запускают мок в транзакции события. Просрочки и приближение дедлайна проверяются фоновыми задачами. Интервал событийных запусков проверяется по сохранённой истории и переживает перезапуск; ручной запуск интервалом не ограничивается. Отключённый триггер возвращает `TRIGGER_DISABLED`, выключенный советник — `AI_DISABLED`.

API: `GET/POST /api/v1/projects/{project_id}/ai/preview`; POST принимает `AiRunRequest` (`trigger`, `question`). `POST /ai/run` принимает тот же запрос; рекомендации возвращают `request_context` (у старых записей — `null`).

## Проверка Telegram

Внизу «Настроек» администратор открывает песочницу и журнал мок-сообщений: время, тип события, текст и упоминания. Можно выбрать демо-проект или текущий проект. Назначение задачи, блокеры, эскалации, закрытие инцидента, просрочки и мок-рекомендации записываются в `telegram_deliveries` в одной транзакции с событием. Это предполагаемые сообщения; реальной отправки нет. Расширенный стенд и очистка описаны в [12-sandbox.md](12-sandbox.md).

Сценарий `mock_notifications` создаёт тестовые события только в проекте Sandbox. После запуска выбрать Sandbox в верхнем списке и обновить сообщения. Фоновая проверка просрочек этого сценария ограничена Sandbox и не меняет рабочие проекты.

Сценарий `create_team` показывает фактические логины тестовых аккаунтов. Отключённые аккаунты не реактивируются: для них создаются тестовые замены с префиксом `sandbox_` (пароль `sandbox-pass`).

API журнала: `GET /api/v1/admin/sandbox/telegram?project_id=...&limit=100` (только администратор; без project_id — все проекты, максимум 500 записей).

## Дополнительные исправления

- Миграция правил таймеров обновляет заполненную SQLite без потери данных; ошибки запуска видны в логах uvicorn.
- Исправлено падение формы инцидента; сборка UI включает TypeScript.
- Пользовательские колонки и их названия доступны в формах создания и перемещения задач.
- Счётчики проекта и участников больше не смешивают данные разных проектов.
- API документов запрещает выход в соседний каталог с совпадающим началом имени, например из `1` в `10`.

## Проверки

Backend: `cd backend; ../.venv/Scripts/python.exe -m pytest -q` (Windows). Тесты используют отдельную базу, рабочие данные не пересоздаются. Frontend: `cd frontend; npm test; npm run build`.

Тесты прав покрывают межпроектный доступ, роли капитана, назначения, метрики и повторную выдачу роли. Тест миграции обновляет заполненную отдельную SQLite. Тесты моков проверяют сохранение контекста, журнал Telegram и изоляцию сценария Sandbox; тесты компонентов проверяют форму инцидента, пользовательские колонки и представление запроса ИИ.
