# Frontend (as-built)

Документ описывает фактический SPA-клиент в `frontend/`, а не первоначальный замысел. Источник истины — код; продуктовые требования остаются в [../docs/06-UI.md](../docs/06-UI.md) и [../docs/02-functional-requirements.md](../docs/02-functional-requirements.md). Контракты API сверены с `backend/app/api/`; полный справочник — [03-api.md](03-api.md).

Источники: `frontend/src/App.tsx`, `Board.tsx`, `Incidents.tsx`, `Analytics.tsx`, `Admin.tsx`, `Settings.tsx`, `Sandbox.tsx`, `ui.tsx`, `api.ts`, `index.css`, `main.tsx`, `frontend/index.html`, `package.json`, `vite.config.ts`, `tsconfig.json`; для сверки — `backend/app/api/*.py`, `backend/app/schemas.py`, `backend/app/deps.py`.

Dev-прокси (`vite.config.ts`):

| Префикс | Куда | Назначение |
| --- | --- | --- |
| `/api` | `http://127.0.0.1:8000` | Все запросы API |
| `/health` | `http://127.0.0.1:8000` | Healthcheck, фронтенд его не вызывает |

Порт dev-сервера — 5173. Backend запускается отдельно на `127.0.0.1:8000`. CORS в backend разрешает `http://localhost:5173` и `http://127.0.0.1:5173` с credentials, но при dev-прокси браузер обращается к тому же origin, поэтому CORS обычно не задействуется.

Цепочка загрузки: `index.html` → `<div id="root">` → `src/main.tsx` → `createRoot(...).render(<StrictMode><App /></StrictMode>)`. `StrictMode` в dev монтирует эффекты дважды, поэтому стартовые запросы (`/auth/me`, проекты, уведомления) в dev дублируются.

Сборка не является самодостаточным деплоем:

- backend не монтирует `frontend/dist` и не раздаёт статику (`backend/app/main.py` содержит только API-роутеры и `/health`);
- в `vite.config.ts` задан только `server.proxy`, но не `preview.proxy`, поэтому `npm run preview` не проксирует `/api` и без внешнего reverse proxy собранный SPA не работает;
- Dockerfile копирует только `backend/`, frontend в образ не попадает; утверждение README о доступности приложения на `127.0.0.1:8000` в Docker относится к API, а не к UI;
- `npm run build` не запускает `tsc`, поэтому ошибки типов не блокируют сборку. Текущий `tsc --noEmit` падает (см. §5.4 и §11).

`tsconfig.json`: `target`/`lib` ES2020, `module` ESNext, `moduleResolution: bundler`, `isolatedModules`, `resolveJsonModule`, `skipLibCheck`, `useDefineForClassFields`, `noEmit`; `include: ["src"]`. Отдельного `tsconfig.node.json`, `vite-env.d.ts`, path-алиасов и ESLint-конфига нет.

Глобального стора, контекста, кеша ответов, нормализации и инвалидаций нет. При монтировании экран заново запрашивает данные; при переключении вкладки компонент размонтируется (условный рендер), его состояние теряется.

### 3.2. `useLoad`

```ts
useLoad<T>(fn, deps = []): [T | null, string, () => void]
```

- при монтировании и при изменении `deps` вызывает `fn()`;
- `data` начинается с `null`, `error` — с `''`;
- успех пишет `setData`, ошибка — `setError(e.message)`;
- успешный повторный запрос **не очищает** прежнюю ошибку;
- `reload` создаётся заново на каждом рендере и не мемоизирован;
- загрузочного флага нет: `null` означает и «ещё не загружено», и «ошибка»;
- `useEffect` подавляет `exhaustive-deps`, поэтому `fn` не обязан быть стабильным.

Следствие: в `Incidents` и `Analytics` эффект `useEffect(..., [reload])` пересоздаёт `setInterval` после каждого рендера, включая рендер от самого опроса. Интервал фактически отсчитывается заново после последнего обновления, а не идёт фиксированным тактом. В `Board` интервал стабилен, потому что `reload` обёрнут в `useCallback`.

### 3.3. Опрос и разовые загрузки

| Данные | Где | Интервал | Комментарий |
| --- | --- | ---: | --- |
| Уведомления | `App` | 10 с | Глобальный `/notifications`, без фильтра по проекту; работает на всех вкладках |
| Задачи + dashboard | `Board` | 1 с | `Promise.all([api.tasks(), api.dashboard()])`; ошибки опроса проглатываются |
| Колонки | `Board` | один раз | При монтировании; изменения колонок в другой вкладке не подхватываются |
| Инциденты | `Board` | один раз | Используются для бейджей «заблокирована/затронута»; после создания инцидента в другой вкладке бейджи устаревают |
| Участники, модули | `Board` / формы | один раз | Дублируются в `Board`, `TaskForm`, `Incidents` |
| Инциденты | `Incidents` | 5 с | Перезагрузка списка; выбранная панель хранит снимок объекта |
| Аналитика | `Analytics` | 5 с | Рекомендации ИИ не опрашиваются |
| Рекомендации ИИ | `Analytics` | один раз | Обновляются вручную после `runAi` |
| Админ-списки | `Admin` | без опроса | Обновление после действий |
| Настройки | `Settings` | без опроса | Обновление после действий |
| Песочница | `Sandbox` | без опроса | Журнал обновляется после запуска |

Интервалы не приостанавливаются при скрытой вкладке (`document.visibilityState` не используется), запросы не отменяются (`AbortController` нет), при медленном ответе возможны наложения. На доске это до трёх запросов в секунду.

### 3.4. Мутации и согласованность

- Кеша и оптимистичных обновлений нет, кроме уведомлений: «прочитано» и удаление меняют локальный массив сразу после успешного ответа, без повторной загрузки.
- Остальные действия идут на сервер и затем вызывают `reload()`/`reloadRecs()`; результат `reload` в обработчиках часто не ожидается.
- `Board` после `moveTask`/`timer` вызывает `reload()` без `await`, поэтому секундный опрос может перезаписать локальное состояние раньше, чем придёт ответ.
- `TaskPanel` отправляет `version` в `patchTask`/`moveTask`. При параллельном изменении сервер вернёт `409 VERSION_CONFLICT`; UI показывает текст ошибки и не предлагает merge/повтор.
- Ошибки многих фоновых загрузок игнорируются: второй элемент `useLoad` не запрашивается в `Board` (участники/модули/инциденты), `Analytics` (рекомендации), `Admin` (роли, журнал входов), `Sandbox` (журнал), `TaskPanel` (история).

### 3.5. Проект и `localStorage`

- Ключ — `hcc-project`, значение — строковый id, по умолчанию `1`.
- `currentProject()` парсит число и принимает только конечное `> 0`, иначе возвращает `1`; `setCurrentProject()` пишет строку.
- `App` инициализирует `projectId` из `currentProject()`, показывает `<select>` со всеми проектами из `GET /projects` и при переключении вызывает `setCurrentProject`, `setProjectId` и `setTab('board')`.
- Экраны получают `key={projectId}`, поэтому переключение полностью размонтирует и заново загружает экран.
- `Settings` читает `localStorage` напрямую (`ProjectSection`, `CompletionSection`), а не принимает `projectId` пропом; это работает только потому, что компонент перемонтируется по `key`.
- Ключ не привязан к пользователю: после выхода и входа другого пользователя на той же машине проект сохраняется. Если id отсутствует в списке (удалён/недоступен), `select` показывает пустое значение, а запросы уходят на этот id; отдельной обработки нет.
- Список проектов бэкенд отдаёт без фильтра по членству (`GET /projects` доступен любому аутентифицированному), поэтому в переключателе видны все проекты.

## 4. Слой API

### 4.1. `request()`

```ts
fetch(path, { credentials: 'include', headers: { 'Content-Type': 'application/json' }, ...init })
```

- URL всегда относительный (`/api/v1/...`), базовый адрес не настраивается; в dev работает через прокси.
- `credentials: 'include'` обязателен: сессия — HttpOnly-cookie `session`; JS токен не видит.
- `Content-Type: application/json` ставится и для GET/DELETE без тела.
- Успех всегда разбирается как `res.json()`; сценария `204 No Content` нет.
- Ошибка: сначала читается тело `{ "error": { "code", "message", "details" } }`; при не-JSON используется `statusText` и код `HTTP_ERROR`. Поле `details` в `ApiError` не сохраняется.
- `ApiError` содержит `status`, `code`, `message`; `instanceof ApiError` используется только на экране входа.
- Нет таймаутов, ретраев, отмены, дедупликации, глобальной обработки `401` и редиректа на вход. Истёкшая сессия проявляется как ошибки на экранах, а `me` остаётся заполненным до перезагрузки.
- CSRF-заголовка нет; защита опирается на SameSite=Lax cookie и JSON-тело.

### 4.2. DTO и типы

Типы объявлены в `api.ts` и не генерируются из OpenAPI. Основные: `Role`, `Me`, `Project`, `Column`, `Assignee`, `Timer`, `Task`, `Incident`, `Notification`, `AiSettings`, `Recommendation`, `UserInfo`, `Participant`, `Module`, `Analytics`, `DashboardKpi`.

## 5. Экраны и поведение

### 5.1. Вход и оболочка

Старт: `App` рендерит «Загрузка…», вызывает `api.me()`. При ошибке `me = null` и показывается `Login`; при успехе — рабочая оболочка. Отдельного маршрута `/login` нет.

`Login`: поля «Логин» и «Пароль» (`type="password"`, `autoComplete`), кнопка «Войти», блокировка на время запроса, сообщение из `ApiError.message`. После `api.login` повторно вызывается `api.me`, результат отдаётся в `onLogin`. Выход — `api.logout`, локальный `setMe(null)`.

Верхняя панель (`topbar`, sticky):

| Элемент | Поведение |
| --- | --- |
| Бренд «Hackathon Command Center» | Статичный текст |
| Селектор проекта | Все проекты; переключение сбрасывает вкладку на «Доска» |
| Вкладки | «Доска», «Инциденты», «Аналитика», «Админ», «Песочница», «Настройки» |
| Уведомления | Кнопка с счётчиком непрочитанных и выпадающим списком |
| Пользователь | Кнопка «{display_name} · Выйти» |

Видимость вкладок:

| Вкладка | Условие показа | Условие рендера |
| --- | --- | --- |
| Доска | всегда | всегда |
| Инциденты | всегда | всегда |
| Аналитика | всегда | всегда |
| Админ | `isAdmin` | `isAdmin` |
| Песочница | **всегда** (фильтр исключает только `admin`) | `isAdmin` |
| Настройки | всегда | всегда |

Баг: неадминистратор видит вкладку «Песочница», но при клике получает пустую область, так как рендер обёрнут в `isAdmin`. Серверные маршруты песочницы при этом защищены `require_admin`.

Состояние `tab` не синхронизируется с URL: нет history, back/forward, deep links, восстановления вкладки после F5. Заголовок проекта, этап и дедлайн в topbar не показываются.

`Board` загружает колонки, задачи и dashboard при монтировании; далее раз в секунду обновляет только задачи и dashboard. Колонки и инциденты для бейджей не обновляются.

Drag-and-drop:

- нативный HTML5: `draggable` на карточке, `onDragStart` пишет `draggingId`, `onDragOver`/`onDrop` на колонке;
- порядок внутри колонки не хранится и не меняется;
- при переносе в `in_progress`, `testing`, `review` вызывается `window.confirm`, если есть незавершённые предшественники типа `blocked_by` или `after`; `before` не считается блокировкой, подзадачи не проверяются;
- завершёнными считаются только `done` и `realised`; `trashed` — нет;
- отказ в `confirm` отменяет перенос; сервер зависимости не проверяет и переход не блокирует;
- то же предупреждение используется в `select` карточки и в боковой панели.

Карточка задачи:

| Элемент | Фактически |
| --- | --- |
| Заголовок | Название |
| Бейджи | «заблокирована» (красный), «затронута» (жёлтый), «просрочена» (красный) |
| Приоритет | Английское значение (`low`/`medium`/`high`/`critical`) с цветом |
| Теги | Синие бейджи |
| Исполнители | Инициалы в кружках |
| Таймер | Кнопки старт/пауза/стоп и `total_seconds` |
| Колонка | `select` из жёстко заданных 9 ключей |
| Модуль, дедлайн, прогресс подзадач | Не показываются; дедлайн виден только как бейдж просрочки |

Бейджи блокировки: `blockedIds` — задачи, на которые ссылается незакрытый инцидент с `target_type === 'task'`; `affectedIds` — транзитивное замыкание по всем `predecessors`, включая `before`. Инциденты с целями `user`/`module` доску не подсвечивают. Так как инциденты загружаются один раз, статус бейджей может устареть до перемонтирования экрана.

Форма создания задачи (модальное окно):

| Поле | Поведение |
| --- | --- |
| Название | Обязательное, проверяется только на пустоту |
| Описание | `textarea` |
| Приоритет | `low`/`medium`/`high`/`critical`, по умолчанию `medium` |
| Колонка | Жёстко заданные 9 стартовых ключей, по умолчанию `backlog` |
| Модуль | Из `GET /modules`, опционально |
| Оценка | Строка `ч:мм`, парсится `hmToSeconds`; неверный формат молча даёт `null` |
| Дедлайн | `datetime-local`, преобразуется в ISO через `new Date(...).toISOString()` |
| Теги | Через запятую, обрезаются, пустые отбрасываются |
| Исполнители | Чекбоксы; первый отмеченный становится основным |

Создание выполняется двумя запросами: `POST /tasks`, затем `PUT /assignees`. Если второй упал, задача уже создана, а форма показывает ошибку; повторное нажатие создаст дубль. `parent_id` в форме не задаётся. Кнопка блокируется на время запроса; ошибка показывается в форме.

Кастомные колонки: `Board` группирует задачи по `column_id` и поэтому отображает их правильно, но `TaskCard` и `TaskForm` используют константу `COLUMN_KEYS` из 9 стартовых ключей. Новая колонка не появляется в этих `select`, а задача в ней показывает пустое/чужое значение. Боковая панель использует реальный список `columns` и работает корректно.

Ошибки: баннер `error` показывается над доской, но не очищается при последующем успехе; ошибки фонового опроса проглатываются. После успешного переноса/таймера `reload()` не ожидается.

### 5.3. Боковая панель задачи

Открывается кликом по карточке, закрывается по крестику или клику по прозрачному backdrop. Ширина 460 px, `max-width: 92vw`, прокрутка внутри. Панель не блокирует доску и не имеет защиты от потери несохранённого текста.

| Секция | Содержимое и действия |
| --- | --- |
| Заголовок | Инлайн-редактирование названия: сохранение по `blur`/Enter через `PATCH /tasks/{id}` |
| Свойства | Колонка (`move`), приоритет (`patch`), модуль (`patch`); бейдж статуса, приоритет и дедлайн в шапке |
| Описание | `textarea` + кнопка «Сохранить описание»; сохраняется только при отличии от серверного |
| Исполнители | Чекбоксы по всем участникам; отмеченные отправляются полным списком; основной — первый в списке, отдельного выбора основного нет |
| Время | Старт/пауза/стоп, `total_seconds`, план `secondsToHm`; корректировка абсолютного накопленного времени в часах (шаг 0.5) только для captain/admin |
| Чек-лист | Добавление, отметка, удаление; редактирования текста нет |
| Связи задач | Список предшественников с типом и статусом, удаление; добавление типа `blocked_by`/`after`/`before`; обратные связи только для чтения |
| Подзадачи | Список задач с `parent_id`; создание новой подзадачи сразу в `backlog`; перехода к подзадаче нет |
| История | До 100 записей аудита: `action`, время, сырой JSON `data`; `actor_id` не преобразуется в имя, ошибки загрузки игнорируются |

Особенности:

- корректировка времени задаёт `accumulated_seconds` целиком, а не дельту; подтверждения и отмены нет;
- при изменении названия/описания локальный `useState` инициализируется один раз и не синхронизируется с опросом; чужие изменения в открытой панели могут быть перезаписаны;
- при `409 VERSION_CONFLICT` показывается сообщение, повторной загрузки и merge нет;
- секции «Обсуждение» у задачи нет (в backend её тоже нет);
- проверки циклов зависимостей нет ни в UI, ни в API (запрещена только зависимость от самой себя);
- чек-лист и подзадачи не влияют на предупреждение при перемещении.

### 5.4. Инциденты

Список: `GET /incidents`, опрос 5 с; участники, задачи и модули — один раз. Фильтр — один `select`, совмещающий статусы (`open`, `confirmed`, `resolved`) и уровни (`yellow`, `red`); одновременно можно выбрать только одно значение. Нет фильтров по ответственному, модулю, области и поиску.

Строка списка: бейдж уровня, бейдж статуса, заголовок, возраст (`age_seconds` на момент ответа), ответственный, автор. ID, область, последнее изменение не показываются. Неподтверждённый красный в списке отображается как жёлтый (`badgeForStatus('open')`), что соответствует смыслу «запрос эскалации».

Критический дефект формы создания: `IncidentForm` использует `error` и `setError`, но не объявляет их. `tsc --noEmit` даёт ошибки `TS2304` в строках 145 и 158 и `TS2552` в строке 239. В рендере выражение `{error && ...}` бросает `ReferenceError`; error boundary отсутствует, поэтому React размонтирует корень и экран становится пустым. Создание инцидента через UI неработоспособно, пока дефект не исправлен.

Поля формы (когда она откроется): уровень (`yellow`/`red`), заголовок, описание, область влияния, срочность (`low`…`critical`, по умолчанию `medium`), ответственный, набор затронутых задач (поиск по названию, фильтр по колонке из 6 ключей, «мои»), участники, модули. Цели складываются в массив `targets` с типами `task`/`user`/`module`. Кнопка «Создать» не блокируется и не проверяет пустой заголовок на уровне UI (только ранний `return`).

Панель инцидента:

- данные берутся из снимка `selected`, сделанного при клике; фоновый опрос список обновляет, но открытую панель — нет;
- показывает ID, заголовок, уровень, статус, дату создания, описание, влияние, срочность, автора, ответственного, решение, цели и журнал;
- для `level === 'red' && status === 'open'` есть кнопки «Подтвердить (глобальная)» и «Отклонить эскалацию»; отклонение отправляет фиксированный комментарий «Отклонено капитаном», поля комментария нет;
- для любого незакрытого инцидента есть поле «Итог решения…» и кнопка «Закрыть»;
- после любого действия панель закрывается и список перезагружается;
- журнал показывает сырые `event_type` (`created`, `confirmed`, `rejected`, `resolved`, `comment`), имя автора и текст из `data.text`/`data.resolution`/`data.comment`;
- ссылок на связанные задачи/модули нет, только текстовые бейджи.

Права в UI не проверяются: кнопки подтверждения и закрытия видны всем. Сервер сам отклоняет действия: подтверждение красного — только captain/admin, закрытие красного — captain/admin, закрытие жёлтого — ответственный или captain/admin. Ошибка `403` показывается в панели. Подтверждений перед подтверждением/закрытием нет.

Несогласованность отображения: в панели неподтверждённый красный получает красный бейдж (`badgeForStatus('red')`), в списке — жёлтый; в аналитике — тоже красный. Один и тот же статус выглядит по-разному.

### 5.5. Аналитика

`Analytics` опрашивает `GET /analytics` каждые 5 с; рекомендации загружает один раз. При отсутствии данных показывает ошибку или «Загрузка…»; ошибка после успешной загрузки не отображается.

KPI:

| KPI | Поле | Примечание |
| --- | --- | --- |
| Прогресс | `progress_percent` | — |
| Задач | `total_tasks` | — |
| Завершено | `completed_tasks` | — |
| В работе | `in_progress_tasks` | — |
| Просрочено | `overdue_tasks` | Красный при `> 0` |
| До дедлайна | `deadline_seconds_left` | `fmtDuration`; отрицательное значение обрезается до `0м`, слово «просрочено» не показывается; красный при `< 6 ч` |
| План / Факт | `estimate_seconds` / `actual_seconds` | `fmt()` |
| Календарное | `calendar_seconds` | `fmt()` |

Фильтров периода, участников, модулей и статусов нет; индикатора автообновления, времени последнего обновления и экспорта нет. Кнопка «Обновить» перезагружает только аналитику.

Burn-down: `LineChart` по `data.burn_down` рисует две линии — `remaining` (акцент) и `completed` (зелёный), точки только для `remaining`, подписи дат через равные интервалы. `maxY` считается только по `remaining`; если `completed > remaining`, зелёная линия выходит выше области графика и обрезается. Третьей линии (`created`) и прогноза нет; легенда — только цветные подписи.

Время по участникам: `BarList` по `time_by_user`, максимум — первый элемент (список отсортирован по убыванию). Время задачи относится к основному исполнителю; соисполнители в этой колонке не учитываются.

Модули: `BarList` со значением `progress` и `max: 100`, подпись `done/total`; клика и перехода к задачам модуля нет.

Риски и блокеры: показываются `active_incidents` (бейдж + заголовок) и `risks` с `type === 'overdue'`. Риски типа `incident` в `risks` дублируются `active_incidents` и отдельно не рендерятся. Ссылок на исходные задачи/инциденты нет; пустое состояние «Рисков нет» проверяет только длины массивов.

Участники: таблица `display_name (login)`, светофор, активные задачи, текущий таймер, «Время всего» из `time_by_user`. Нагрузка, роли, блокеры не показываются.

Рекомендации ИИ: до 10 последних, `summary`, `trigger`, дата, `content`; кнопка «Запросить анализ» вызывает `POST /ai/run` и перезагружает список. Кнопки подробностей и переключателя `excluded` нет; история ограничена ответом API (по умолчанию 50).

### 5.6. Админка

Доступна только при наличии роли `admin` (вкладка скрыта, сервер требует `require_admin`). Внутренние разделы переключаются кнопками.

| Раздел | Фактически |
| --- | --- |
| Пользователи | Таблица ID/логин/имя/Telegram/роли/статус/действия; создание; назначение ролей; сброс пароля; деактивация |
| Журнал входов | Последние 100 записей: время, логин, IP, успех/отказ, причина; без фильтров и обновления |
| IP-ограничения | Форма ввода IP: заблокировать, сбросить лимит; список правил и разблокировка отсутствуют |
| Резервные копии | Создание, список, восстановление; запуск фоновых jobs |

Пользователи:

- роли показываются бейджами (admin — красный, captain — жёлтый, participant — синий) с кнопкой отзыва и `confirm`;
- кнопки «участник», «капитан», «админ» назначают роль, если её ещё нет;
- **назначение participant/captain идёт с `project_id: null`**, потому что `Admin` не передаёт проект: `api.assignRole(u.id, 'participant')`. Это глобальная роль, а не проектная, что расходится с моделью «participant/captain привязаны к проекту»;
- `project_id` существующих назначений в таблице не отображается, поэтому проектные роли из песочницы выглядят как обычные;
- новый пароль запрашивается через `window.prompt` и передаётся открытым текстом; поле пароля при создании пользователя — обычный `input` без `type="password"`;
- редактирования логина/имени/Telegram нет, хотя `PATCH /admin/users/{id}` существует и `api.patchUser` объявлен;
- реактивации нет: backend не принимает `active` в PATCH, кнопка «отключить» исчезает после деактивации;
- ошибки назначения/отзыва роли и сброса пароля не перехватываются (unhandled rejection), сообщений нет; защита последнего администратора работает только на сервере (`409 LAST_ADMIN`) и в UI не отображается.

Журнал входов: `useLoad` один раз, клиентский `slice(0, 100)`; пагинации, поиска и автообновления нет. API по умолчанию уже отдаёт 100 записей.

IP: список заблокированных IP не запрашивается (эндпоинта списка нет), разблокировка недоступна. Пустой IP или повторная блокировка приводят к необработанной ошибке, сообщение об успехе не показывается.

Бэкапы: таблица ID/создан/тип/действие; `kind` окрашивается (`safety`, `manual`, остальные серые). Размер, checksum и путь не показываются. Восстановление подтверждается `confirm`, но список после него не перезагружается, а состояние приложения не обновляется. Создание бэкапа и запуск jobs не обрабатывают ошибки. Раздела аудита нет.

### 5.7. Настройки

Доступны всем; часть действий ограничена ролями. Контейнер `maxWidth: 720`.

| Секция | Содержимое | Ограничения UI |
| --- | --- | --- |
| Проект | Бейдж состояния, дедлайн; переименование; дедлайн; создание проекта | Название — captain/admin, дедлайн и создание — admin |
| Колонки доски | Таблица: переименование по `blur`, чекбоксы авто-старта/авто-стопа, удаление, добавление | Без ограничения по роли; стартовые 9 колонок защищены сервером |
| Модули | Создание, переименование по `blur`, удаление, бейдж светофора | Описание только показывается, не редактируется |
| Завершение | Голос за завершение/повторное открытие, сообщение с числом голосов | Кнопка недоступна без captain/admin; повторное открытие без подтверждения |
| ИИ | Вкл/выкл, провайдер Gemini/DeepSeek, интервал (мин), сохранение | Только captain/admin; `prompt` и `triggers` не редактируются |

Проект:

- имя и дедлайн не подставляются в поля: имя инициализируется из текущего проекта, дедлайн — пустой, поэтому при изменении дедлайна нужно вводить значение заново;
- `deadline_msk` формируется как `new Date(deadline).toISOString()`: `datetime-local` интерпретируется в часовом поясе браузера, а не в MSK; при не-московском поясе дедлайн сдвигается;
- созданный проект не выбирается автоматически, сообщение предлагает выбрать его в списке сверху;
- ошибки сохранения не перехватываются;
- состояние `completed` только отображается бейджем; UI не переключается в read-only.

Колонки:

- переименование и чекбоксы сохраняются сразу, без подтверждения;
- удаление подтверждается, задачи переносятся в `backlog` на сервере;
- ошибка удаления попадает в `setMsg` и выглядит как успешное зелёное сообщение;
- новый ключ генерирует сервер (`slug`), UI его не знает; после добавления колонка появится на доске только при её следующем монтировании;
- `defaultChecked`/`defaultValue` означают, что локальная ошибка сохранения не откатывает визуальное состояние до перезагрузки.

Модули: создание с названием и описанием, переименование, удаление с подтверждением; описание после создания не редактируется, хотя API это позволяет.

Завершение: текст обещает единогласное голосование капитанов; UI не показывает список проголосовавших и не даёт отозвать голос. Для завершения есть `confirm`, для повторного открытия — нет.

ИИ: секция возвращает `null`, пока настройки не загрузились или упали, поэтому ошибка выглядит как отсутствие блока. Сохраняются только `enabled`, `priority_provider`, `interval_minutes`; `prompt` и `triggers` из `AiSettings` не используются. Сохранение не обёрнуто в `try/catch`.

Экран предназначен для администратора, но вкладка видна всем (см. §5.1). Показывает:

### 5.9. Уведомления

Живут в `App`, опрос 10 с, эндпоинт глобальный (не по проекту). Кнопка с колоколом и счётчиком открывает выпадающий список; закрытие — повторным кликом, клика вне и Escape нет.

Возможности: «Прочитать все», «Очистить все», удалить одно, отметить одно прочитанным. «Прочитать все» ставит локальный `read_at = 'now'`; удаление и очистка меняют массив локально после успешного ответа. Ошибки не перехватываются.

Отображается: тип (русская подпись для шести известных типов), `payload.title`, `payload.resolution` при наличии, дата. Ссылки на задачу/инцидент и фильтра по проекту нет; уведомления других проектов выглядят так же. Подтверждения для «Очистить все» нет.

## 6. UI-примитивы и форматирование

| Примитив | Сигнатура/поведение |
| --- | --- |
| `useLoad` | Загрузка с `data`/`error`/`reload`; см. §3.2 |
| `fmt` | Секунды → `ч:мм:сс`, отрицательные обрезаются до 0 |
| `fmtDuration` | Секунды → `Dд Hч`, `Hч Mм` или `Mм`; отрицательные → `0м` |
| `secondsToHm` | Секунды → `Hч Mм` или `Mм` |
| `hmToSeconds` | `H:MM` (1–3 цифры часов, ровно 2 цифры минут) → секунды; иначе `null` |
| `parseUTC` | Если строка не содержит `Z` или смещение `±чч:мм`, дописывает `Z` |
| `fmtDate` | `null` → «—»; иначе `toLocaleString('ru-RU', { day/month 2-digit, hour/minute 2-digit })` |
| `Modal` | Backdrop, клик по нему закрывает; клик внутри остановлен; заголовок и крестик; без Escape и focus trap |
| `Field` | `<label class="field">` с подписью и контролом |
| `Badge` | `<span class="badge {kind}">` |
| `badgeForStatus` | `green/resolved/done/realised` → green; `yellow/open` → yellow; `red/confirmed` → red; `running` → blue; иначе gray |
| `LineChart` | SVG 640×200, сетка, две линии (`remaining`, `completed`), точки по `remaining`, подписи дат |
| `BarList` | Горизонтальные бары: label 160 px, трек, значение 90 px; ширина ограничена 100% |

Правило UTC: backend хранит наивный UTC и отдаёт ISO без суффикса. `parseUTC` добавляет `Z`, чтобы `Date` не истолковал строку как локальное время. Правило применяется к `task.deadline`, `created_at`, `deadline_msk`, событиям инцидентов и уведомлениям. Если строка уже содержит `Z` или смещение, она не меняется.

Ограничение: `fmtDate` форматирует в часовом поясе браузера, а не в MSK. Продукт называет дедлайн `deadline_msk` и подразумевает московское время; при работе из другого пояса отображение и ввод дедлайна смещаются. Отдельной конвертации в `Europe/Moscow` нет.

`LineChart` не имеет подписей оси Y, значений в точках, tooltip и легенды (легенда собрана вручную в `Analytics`). `BarList` не обрезает отрицательные значения и не форматирует числа сам — получает готовый `display`.

## 8. Разграничение прав в UI

UI определяет роль по плоскому списку `me.roles`:

- `isAdmin` — есть роль `admin`;
- `isCaptain` — есть `captain` или `admin`.

`project_id` у роли нигде не проверяется: одна и та же роль считается действующей для любого выбранного проекта. Это совпадает с фактическими серверными зависимостями (`require_captain_or_admin`, `require_member` проверяют набор ролей без привязки к проекту), но расходится с продуктовой моделью проектных ролей.

| Действие | UI | Сервер |
| --- | --- | --- |
| Вкладка «Админ» | скрыта без admin | `require_admin` |
| Вкладка «Песочница» | видна всем, контент только admin | `require_admin` |
| Создание/редактирование задач, чек-лист, связи, исполнители | доступно всем | `require_member` (любая роль) |
| Перемещение задачи | доступно всем | `require_member`, проверка активного проекта |
| Таймер start/pause/stop | доступно всем | `require_member` |
| Корректировка времени | скрыта без captain/admin | `require_captain_or_admin` |
| Подтверждение/отклонение красного | видно всем | только captain/admin, иначе 403 |
| Закрытие инцидента | видно всем | жёлтый — ответственный или captain/admin; красный — captain/admin |
| Создание инцидента | доступно всем | любой аутентифицированный, активный проект |
| Переименование проекта | поле доступно captain/admin | captain/admin |
| Дедлайн проекта | поле доступно admin | только admin |
| Создание проекта | блок admin | только admin |
| Колонки и модули | доступно всем | `require_member` |
| Завершение/открытие проекта | кнопка disabled без captain/admin | `require_captain_or_admin` |
| Настройки ИИ | изменения disabled без captain/admin | чтение — любой, запись — captain/admin |
| Роли, пользователи, IP, бэкапы | только admin | `require_admin` / `require_captain_or_admin` для бэкапов и jobs |

Дополнительно:

- `/projects/{id}/participants` на сервере выбирает всех активных пользователей с любой активной ролью без фильтра по проекту; поэтому фильтр исполнителей, список ответственных и исполнителей задачи глобальны. `/projects` также отдаёт все проекты.
- Роли participant/captain, назначенные через админку, получают `project_id = null`; проектные назначения можно создать только через песочницу или API.
- В завершённом проекте UI не переходит в read-only: кнопки остаются активными. Сервер отвечает `409 PROJECT_COMPLETED` только на часть операций (создание/перемещение задачи, таймеры, исполнители, зависимости, создание/подтверждение/закрытие инцидента). `PATCH /tasks/{id}`, чек-лист, колонки, модули, настройки ИИ и переименование проекта такой проверки не содержат, поэтому часть редактирования в completed-проекте проходит.
- Скрытие кнопок — UX, а не безопасность: сервер остаётся источником истины и проверяет права повторно. Обратная сторона — UI местами показывает недоступные действия и получает 403/409.

## 10. Как добавить экран, вкладку или метод API

1. **Backend-контракт.** Добавить роутер/обработчик в `backend/app/api/`, Pydantic-схемы в `schemas.py`, при необходимости модель и Alembic-миграцию. Описать маршрут, права и ошибки в [03-api.md](03-api.md); фоновые эффекты — в [05-jobs-and-integrations.md](05-jobs-and-integrations.md).
2. **DTO и метод.** В `frontend/src/api.ts` добавить интерфейс ответа и метод в `api`. Для проектных маршрутов использовать `pid()`; не забыть `credentials` (он уже в `request`) и явный generic, иначе TypeScript получит `unknown` (текущая ошибка `createTask`).
3. **Компонент.** Создать `frontend/src/NewScreen.tsx`; экспорт default или named — как удобно, но импорт в `App` должен совпадать. Данные грузить через `useLoad`, ошибки показывать рядом с экраном, после мутаций вызывать `reload`.
4. **Вкладка.** В `App.tsx` расширить union `Tab`, массив `TABS`, добавить условие рендера. Для админских вкладок проверять `isAdmin` не только в рендере, но и в `TABS` (сейчас «Песочница» видна всем). Передавать `key={projectId}` для перемонтирования при смене проекта; при необходимости — `me` и `onProjectsChanged`.
5. **Права.** UI-гейт — только UX. Проверку ролей и проектной области делать на сервере; в UI отражать 403/409 понятным сообщением.
6. **Стиль.** Переиспользовать классы `card`, `row`, `grid`, `section`, `badge`, `field`, `board`; новых CSS-модулей нет. Помнить, что медиазапросов нет.
7. **Проверка.** Запустить `npx tsc --noEmit` вручную: `npm run build` типы не проверяет. Автотестов фронтенда нет; сценарий проверяется вручную в dev-сервере.
8. **Документация.** Обновить этот файл и [03-api.md](03-api.md). Пошаговые соглашения разработки должны быть в [../docs/08-development-guide.md](../docs/08-development-guide.md), но **в текущем дереве этого файла нет**; из существующего ближе всего [../docs/03-architecture-and-operations.md](../docs/03-architecture-and-operations.md) и [01-stack-and-layout.md](01-stack-and-layout.md). Также отсутствуют `docs/07-implementation-status.md`, `docs/09-operations-runbook.md`, `docs/10-known-gaps-and-roadmap.md` и `specifications/07-flows.md`, хотя README и спецификации на них ссылаются.

Добавление админ-раздела: расширить `type Section` и массив кнопок в `Admin.tsx`, вынести компонент, использовать `useLoad` и `api`-метод; серверный роутер — под `APIRouter(prefix="/admin", dependencies=[Depends(require_admin)])`.

## 11. Ограничения и техдолг фронтенда

| Область | Проблема | Влияние |
| --- | --- | --- |
| Критический дефект | `IncidentForm` не объявляет `error`/`setError`; `tsc` падает, рендер формы бросает `ReferenceError` | Создание инцидента через UI не работает; без error boundary падает весь экран |
| Типы | `npm run build` не запускает `tsc`; текущий `tsc --noEmit` содержит 5 ошибок (`Incidents.tsx` ×4, `Board.tsx` ×1) | Ошибки типов не блокируют сборку и накапливаются |
| Error boundary | Отсутствует | Любая ошибка рендера размонтирует всё приложение |
| Обновление данных | Polling вместо WebSocket/SSE: 1 с доска, 5 с инциденты/аналитика, 10 с уведомления | Нагрузка, задержки, гонки, устаревшие бейджи и панели |
| Интервалы | В `Incidents`/`Analytics` `reload` нестабилен, эффект пересоздаёт таймер каждый рендер | Плавающий такт опроса |
| Кеш | Нет кеша/дедупликации; одни и те же списки грузятся в `Board`, `TaskForm`, `Incidents`, `Settings` | Лишние запросы |
| Ошибки | `useLoad` не очищает ошибку; часть запросов игнорирует второй элемент кортежа; многие обработчики без `try/catch` | Ошибки теряются или остаются навсегда; unhandled rejection |
| Гонки | `reload()` после мутаций не ожидается; `version`-конфликты не разрешаются | Возможна перезапись локального состояния и 409 без восстановления |
| Пароли | `prompt()` для сброса; поле нового пароля без `type="password"` | Пароль виден на экране и в истории ввода |
| Подтверждения | Нет для подтверждения/закрытия инцидента, jobs, IP, очистки уведомлений, повторного открытия проекта | Риск случайного опасного действия |
| Дублирование типов | DTO в `api.ts` и inline-типы в компонентах; `Backup`, `Run`, роли | Расхождения с API |
| Жёсткие ключи колонок | `COLUMN_KEYS` из 9 значений в карточке и форме создания | Кастомные колонки не выбираются |
| Время | Ввод/вывод в часовом поясе браузера, а не MSK; `deadline_msk` только по имени | Сдвиг дедлайнов при другом поясе |
| График | `maxY` по `remaining`; линия `completed` может уйти за границу | Искажение burn-down |
| Доступность | Кликабельные `div` без клавиатуры/ролей, модалки без focus trap/Escape, иконки-эмодзи | Keyboard/screen-reader сценарии ограничены |
| Мобильность | Нет медиазапросов; таблицы и доска рассчитаны на desktop | На узком экране только горизонтальная прокрутка |
| Тесты | Нет unit/component/e2e тестов и линтера | Регрессии вроде `IncidentForm` не ловятся |
| Монолиты | `Board.tsx` 756 строк, `Settings.tsx` 382, inline-стили | Сложность сопровождения |
| localStorage | `hcc-project` не привязан к пользователю; id не валидируется по списку | Чужой/удалённый проект после смены пользователя |
| Область данных | Списки проектов и участников глобальны; роли participant/captain назначаются без проекта | UI показывает и позволяет больше, чем предполагает проектная модель |
| Завершённый проект | UI не read-only; сервер проверяет не все операции | Часть изменений проходит в completed-проекте |
| Пагинация | Нет; журналы/списки грузятся целиком, логины обрезаются на клиенте | Рост времени рендера |
| Зависимости | Нет проверки циклов; `before` не считается блокировкой | Можно создать циклическую/непредупреждённую связь |
| Сборка/деплой | Нет раздачи `dist` backend'ом, нет `preview.proxy`, Docker без frontend | Собранный SPA не работает без reverse proxy |
| Внешние ресурсы | Google Fonts через `@import` | Офлайн-режим и CSP-ограничения |
| Безопасность | Нет CSRF-заголовка; защита — SameSite=Lax + JSON | Известное ограничение, не только фронтенда |

Приоритет исправлений: сначала `IncidentForm` и включение `tsc --noEmit` в проверку/CI; затем error boundary и обработка ошибок; далее вынос общих DTO, отказ от `prompt`, подтверждения опасных действий; потом WebSocket/SSE и адаптивность.
